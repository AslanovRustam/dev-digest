# Where Business Logic Belongs in a React Frontend: Custom Hooks vs Service Modules vs a Domain Layer

> Scope note: ARCHITECTURE ONLY. Performance, re-render optimization, memoization and bundle size are deliberately excluded, except where a source's own argument is inseparable from them (flagged inline as "perf argument — out of scope").
> Era note: findings reflect React 19 / RSC-era docs (react.dev as of 2026) and the 2020-2026 blog canon. Pre-hooks advice is marked **[SUPERSEDED]**.

## Q1. Are "dumb"/presentational components still the consensus? Is Container/Presentational still recommended? (incl. Dan Abramov's disclaimer)

### Takeaway
The *goal* — components that express intent and don't own business logic — is still consensus; the *mechanism* (a wrapper "container" component) is not. Dan Abramov, who popularized the split in 2015, added an update to his own article saying he no longer suggests splitting components that way because Hooks achieve the same separation "without an arbitrary division." React Server Components have partially revived a container/presentational *shape* (server fetches, client renders), but sources disagree on whether that is the same pattern or a coincidence of the RSC boundary.

### Cited Findings
- Dan Abramov's original article "Presentational and Container Components" (2015) is the canonical source of the pattern — [Dan Abramov, Medium](https://medium.com/@dan_abramov/smart-and-dumb-components-7ca2f9a7c7d0)
- Abramov added a 2019 update to that article stating that he **no longer suggests splitting components into presentational and container components**; his stated reasoning: the main reason he originally found the pattern useful was that it let him separate complex stateful logic from other aspects of the component, and **Hooks let him do the same thing without an arbitrary division**. He also says that if the pattern feels natural in a codebase it can be handy, but that he has seen it "enforced without any necessity and with almost dogmatic fervor far too many times." — [Dan Abramov, "Presentational and Container Components", 2015, updated 2019](https://medium.com/@dan_abramov/smart-and-dumb-components-7ca2f9a7c7d0) — **VERBATIM CAVEAT: see Gaps. Medium returned HTTP 403 to automated fetching; the wording above is reconstructed from search-index extracts of the article plus multiple secondary sources that describe the update. The phrases "almost dogmatic fervor" and "arbitrary division" are attested in the search index of the article itself, but a full character-for-character quotation could not be retrieved. Do not present the whole update as a block quote in the final report.**
- Secondary confirmation that the update exists and what it says: "it seems that even Dan has changed his views on the usefulness of this pattern with the introduction of hooks, as mentioned in the 'updated:' section at the top of that article" — [Sam Dawson, "Goodbye presentational and container components?", 2020-04-22](https://www.samdawson.dev/article/container-components/)
- patterns.dev's verdict: Hooks have superseded the pattern — custom Hooks "achieve identical separation of concerns with less boilerplate", the pattern "risks being overkill in smaller sized applications", and "Modern React strongly favors Hooks over container components" — [patterns.dev, "Container/Presentational Pattern"](https://www.patterns.dev/react/presentational-container-pattern/)
- GreatFrontend's reference answer also states Abramov "no longer recommends splitting components this way" in favour of hooks — [GreatFrontend quiz: presentational vs container](https://www.greatfrontend.com/questions/quiz/explain-the-presentational-vs-container-component-pattern-in-react)
- RSC revival argument, with skepticism: with RSC "developers naturally recreate this split: server components fetch data and handle mutations (container role), while client components receive props and render UI (presentational role)", but the author is skeptical, noting that pushing all markup into client-only components "undermines RSC's primary benefit of reducing JavaScript sent to browsers" — [Lorenzo Rivosecchi, "RSC and the Echo of 'Presentational and Container Components'", dev.to, 2023-06-29 (ed. 2024-02-02)](https://dev.to/fibonacid/rsc-and-the-echo-of-presentational-and-container-components-33i)
- Sam Dawson's own alternative: design components around their **interface/API** (universal / global / view components) rather than around where state lives; he treats "I followed it because it was best practice" as a warning sign — [Sam Dawson, 2020-04-22](https://www.samdawson.dev/article/container-components/)
- Alex Kondov argues against the split explicitly: "Instead of container/presentational splits, think about where state logically belongs — data should live close to its usage point", and "Pulling all the logic in a few components leads to bloat." — [Alex Kondov, "Tao of React", last updated 2021-01-18](https://alexkondov.com/tao-of-react/)
- react.dev's official framing of the same goal, without the pattern name: extracting context/reducer wiring into custom hooks "keeps the components clean and uncluttered, **focused on what they display rather than where they get the data**" — [react.dev, "Scaling Up with Reducer and Context"](https://react.dev/learn/scaling-up-with-reducer-and-context)

### Inferences
- The modern restatement of "dumb components" is not "components without logic" but "components without *hidden* logic": react.dev's `use`-prefix rule exists precisely so a reader can tell, by name alone, where state and effects can hide ([Reusing Logic with Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)). The separation moved from *component boundary* to *function-name convention*.
- RSC changes the *reason* to split (bundle/serialization boundary) rather than restoring the 2015 *rationale* (stateful-logic isolation). Treating the `"use client"` boundary as if it were the container/presentational boundary is an inference the sources support only weakly, and Rivosecchi argues against it.

### Gaps
- **Verbatim Abramov disclaimer not retrievable.** medium.com returns 403 to WebFetch; web.archive.org is blocked in this environment; freedium.cfd did not resolve; scribe.rip returned 404. Original publication date of the article could likewise not be confirmed on-page (commonly cited as March 2015).

## Q2. Custom hooks as the logic layer: what does react.dev officially say, and what are the documented limits?

### Takeaway
react.dev treats custom Hooks as the official mechanism for sharing *stateful logic*, with two hard constraints: a hook shares logic but never state, and hooks must model **concrete, high-level use cases** rather than wrap React's own lifecycle. The documented limits are structural: Hooks may only be called from components and other Hooks, so any logic placed in a hook is permanently coupled to the render cycle and cannot be called from plain functions, event handlers, `try/catch`, or non-React code.

### Cited Findings
- Purpose: custom Hooks exist for cases where "you'll wish that there was a Hook for some more specific purpose: for example, to fetch data, to keep track of whether the user is online, or to connect to a chat room." — [react.dev, "Reusing Logic with Custom Hooks"](https://react.dev/learn/reusing-logic-with-custom-hooks)
- Naming is load-bearing, not cosmetic: "Hook names must start with `use` followed by a capital letter"; "This convention guarantees that you can always look at a component and know where its state, Effects, and other React features might 'hide'." Conversely: "If your function doesn't call any Hooks, avoid the `use` prefix... For example, `useSorted` below doesn't call Hooks, so call it `getSorted` instead." — [react.dev, Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)
- **The key architectural limit**: "Custom Hooks let you share *stateful logic* but not *state itself.* Each call to a Hook is completely independent from every other call to the same Hook." When state must be shared, the docs say to "lift it up and pass it down instead." — [react.dev, Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)
- What SHOULD become a hook: purpose-named, high-level use cases — `useData(url)`, `useImpressionLog(eventName, extraData)`, `useChatRoom(options)`; and wrapping Effects, because "if you're writing one, it means that you need to 'step outside React'... Wrapping it into a custom Hook lets you precisely communicate your intent and how the data flows through it." — [react.dev, Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)
- What should NOT become a hook: "**Keep custom Hooks focused on concrete high-level use cases.** Avoid creating and using custom 'lifecycle' Hooks that act as alternatives and convenience wrappers for the `useEffect` API itself." Named anti-examples: `useMount(fn)`, `useEffectOnce(fn)`, `useUpdateEffect(fn)`. "Custom 'lifecycle' Hooks like `useMount` don't fit well into the React paradigm." — [react.dev, Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)
- Design criterion: "A good custom Hook makes the calling code more declarative by **constraining what it does**", and the name should be clear enough "that even a person who doesn't write code often could have a good guess about what your custom Hook does, what it takes, and what it returns." — [react.dev, Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)
- Intent-hiding is the stated benefit: "you can hide the gnarly details of how you deal with some external system or a browser API. The code of your components expresses your intent, not the implementation." — [react.dev, Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)
- Hooks as a *migration seam*: "If you use custom Hooks like `useData` above in your app, it will require fewer changes to migrate to the eventually recommended approach than if you write raw Effects in every component manually." — [react.dev, Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)
- Hard coupling to React: Hooks may be called only "at the top level in the body of a function component" or "at the top level in the body of a custom Hook". Explicitly forbidden: inside conditions or loops, after a conditional `return`, in event handlers, in class components, inside functions passed to `useMemo`/`useReducer`/`useEffect`, and inside `try`/`catch`/`finally`. "**Don't call Hooks from regular JavaScript functions.**" — [react.dev, "Rules of Hooks"](https://react.dev/reference/rules/rules-of-hooks)
- Testability consequence: a custom hook is not a pure function, so it cannot simply be called and asserted on — calling it directly in a test breaks the rules of hooks and produces `Error: Invalid hook call`; it must be exercised through `renderHook()` (or a dummy component), which adds test infrastructure that a plain module would not need — [Kent C. Dodds, "How to test custom React hooks"](https://kentcdodds.com/blog/how-to-test-custom-react-hooks); corroborated by [LogRocket, "How to test React Hooks"](https://blog.logrocket.com/test-react-hooks/) and [DEV, "Testing a React Custom Hook"](https://dev.to/manuartero/testing-a-custom-hook-like-a-pro-1b19)
- Community critique of over-abstraction into hooks: custom hooks "turn into invisible containers of state, side effects, and assumptions that are no longer obvious at the call site"; the proposed correction is to use hooks "only for mechanical reuse", moving anything that "owned real state or business decisions" elsewhere — [Medium, "Custom React Hooks Are Overused: The React 19 Anti-Pattern..."](https://medium.com/@rahulkengale1110/custom-hooks-are-making-your-react-code-worse-and-most-developers-dont-realize-it-540579277248) — **authority: low (Medium, no institutional standing); use only as evidence that the concern circulates, not as a claim.**
- Complementary rule from a recognized practitioner: "Helper functions shouldn't read from the component's state" — pure functions taking arguments are "easier to debug and extend", and helpers that don't need a closure over the component "should be moved outside" — [Alex Kondov, "Tao of React"](https://alexkondov.com/tao-of-react/)

### Inferences
- react.dev's own guidance implies a two-tier logic layer: **pure functions** (`getSorted`, no `use` prefix, trivially testable, callable anywhere) for computation, and **custom Hooks** for anything that touches React state, subscriptions or external systems. The "avoid the `use` prefix" rule is, read architecturally, an instruction to keep business *rules* out of hooks and put only *wiring* in them.
- "Shares logic, not state" is the single strongest argument against using custom hooks as the app's domain layer: two components calling `useCart()` get two independent carts. Any logic that must be *singular* per app needs a store, context, or a query cache — not a hook alone.
- The Rules of Hooks are the precise, citable form of the "can't reuse outside React" objection: business logic in a hook cannot be reused by a CLI, a worker, a server route, or an event handler without re-implementation.

### Gaps
- react.dev contains no explicit statement about testability of custom hooks vs plain modules; the testability limit is documented only in community/expert sources (Kent C. Dodds being the strongest).

## Q3. Service / API layer: what shape is recommended? And where does Zod-at-the-boundary fit?

### Takeaway
The dominant, documented convention in 2025-2026 is **feature-scoped API modules** (`features/<x>/api/`) exporting a request function plus the hook that wraps it — not a global `services/` directory and not a formal Repository. A repository/ports abstraction appears only in the Clean-Architecture branch of the literature (Q4). Schema validation at the network boundary (Zod `safeParse`, types via `z.infer`) is treated as the natural job of that API module.

### Cited Findings
- Bulletproof React (the most-cited opinionated React architecture reference) puts API code inside features: each feature folder contains `api/` — "API requests and hooks" — alongside `components/`, `hooks/`, `stores/`, `types/`, `utils/` — [Bulletproof React, docs/project-structure.md](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)
- Bulletproof React allows the centralized variant explicitly: "In some cases it might be more practical to keep all API calls outside of the features folders in a dedicated `api` folder where all API calls are defined." — [Bulletproof React](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)
- Bulletproof React enforces layering with tooling, not convention: unidirectional flow **shared → features → app**; "the shared parts can be used by any part of the codebase, but the features can only import from shared parts and the app can import from features and shared parts"; "It might not be a good idea to import across the features. Instead, compose different features at the application level." Enforced via ESLint `import/no-restricted-paths`. — [Bulletproof React](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)
- Robin Wieruch (author of "The Road to React") reaches the same shape by a different route: a top-level `api/` folder for "centralized API client code when many features share the same endpoints"; he does **not** recommend a `services/` folder; single-use hooks stay with their component, shared ones go to `hooks/`. His invariant: "code flows in one direction — from shared utilities into features, and from features into pages. Never the other way around", and features should be "independent and deletable without breaking the system." — [Robin Wieruch, "React Folder Structure in 5 Steps", last updated 2026-05-05](https://www.robinwieruch.de/react-folder-structure/)
- TkDodo colocates the data layer per feature and exports only hooks: query keys and query functions live in `src/features/Profile/queries.ts`, `src/features/Todos/queries.ts`; "Query functions and keys remain local to their feature, with only custom hooks exported." — [TkDodo, "Effective React Query Keys", 2021-06-13 (upd. 2022-04-23)](https://tkdodo.eu/blog/effective-react-query-keys)
- Decoupling rationale for an API layer, from an advocate: a component "shouldn't be aware if we're using `fetch`, `axios`, or another HTTP client", nor "if that data is fetched via HTTP, gRPC... or any other kind of source." — [Alex Kondov, "Clean Architecture in React", 2024-02-09](https://alexkondov.com/full-stack-tao-clean-architecture-react/)
- Zod at the boundary: the pattern is to parse any data entering the system (API response, form, env vars) through a schema, deriving the TS type with `z.infer<typeof Schema>`; `safeParse` is preferred over `parse` in handlers because `parse` throws an unhandled exception on invalid input. Zod is reported at 40M+ weekly npm downloads, i.e. the de-facto ecosystem default. — [Wisp CMS, "Validating API Response with Zod"](https://www.wisp.blog/blog/validating-api-response-with-zod); [laniewski.me, "API Response validation with Zod", 2023-11-19](https://laniewski.me/blog/2023-11-19-api-response-validation-with-zod/); [brenelz.com, "Using Zod To Validate Api Responses"](https://www.brenelz.com/posts/using-zod-to-validate-api-responses/) — **authority: community consensus; no single official source states this as doctrine.**
- The boundary framing itself: "parse at the boundary, with `unknown` in and your validated type out" — [DEV, "Runtime Validation in TypeScript: Where Zod Ends and the Type System Begins"](https://dev.to/gabrielanhaia/runtime-validation-in-typescript-where-zod-ends-and-the-type-system-begins-4e9e)

### Inferences
- "Service layer" as a *name* has largely lost to "api layer" + "custom hook" in the React literature; what Fowler calls a Service Layer is, in practice, split between the API module (transport + validation) and the query hook (caching, orchestration).
- Generated clients (OpenAPI → TS) were not covered by any of the authoritative sources retrieved; the retrieved consensus is hand-written per-resource modules. Treat "generated clients" as an unsettled option, not a recommendation.
- Zod-at-the-boundary is architecturally significant beyond validation: because `z.infer` makes the schema the single source of truth for the type, the schema module becomes the closest thing most React apps have to a *domain model definition* — a cheap alternative to the entities layer of Clean Architecture.

### Gaps
- No authoritative source found for or against **generated API clients** (openapi-typescript, orval, tRPC) as an architectural choice; searches surfaced only tooling docs, not architectural argument.
- No authoritative frontend source found advocating a literal **Repository pattern** by name outside the Clean-Architecture writings in Q4.

## Q4. Does a React app ever warrant an explicit domain layer? (Clean Architecture / hexagonal / DDD on the frontend) — ADVOCATES vs CRITICS

### Takeaway
This is the sharpest disagreement in the material, and it should not be smoothed over. Advocates (Bespoyasov, Kondov) argue for an explicit domain layer with inward-only dependencies; both, notably, attach their own "don't do this on small projects" caveats. Critics argue that the layering imports backend assumptions, multiplies the files touched per change, and mistakenly treats React as an implementation detail when rendering, forms, focus and cache coordination are genuinely part of the frontend model. There is no official React position at all — react.dev never discusses a domain layer.

### Cited Findings — ADVOCATES
- Three layers by proximity to domain knowledge: **Domain** (entities + pure data transformations, independent of externals — "The domain is the core that distinguishes one application from another"), **Application** (use cases orchestrating domain logic through *ports*, i.e. interfaces expressing how the app wants to talk to the outside world), **Adapters** (concrete third-party integrations, isolating the app from external API change). Governing rule: "**Only the outer layers can depend on the inner layers.**" — [Alex Bespoyasov, "Clean Architecture on Frontend", 2021-09-02](https://bespoyasov.me/blog/clean-architecture-on-frontend/)
- Bespoyasov's own limits: a full implementation is inappropriate when the project is small — "A full implementation will be an overkill that will increase the entry threshold for newcomers" — and pragmatism overrides purity: "If it's more pragmatic... to break a rule, I'll break it." He also concedes "The clean architecture can increase the amount of code in the final bundle" (perf/bundle argument — out of scope, recorded only because it is his own caveat). His **minimum viable version**: extract the domain and respect the dependency direction; add the rest incrementally. — [Bespoyasov, 2021](https://bespoyasov.me/blog/clean-architecture-on-frontend/)
- Kondov's justification for layers is rate-of-change, not purity: "We add layers because different kinds of logic change at a different pace, and they shouldn't impact one another." And on the split: "The visualization code is our interface to the browser. When, how, and what data we need is part of our domain logic. They have no place being together." — [Alex Kondov, "Clean Architecture in React", 2024-02-09](https://alexkondov.com/full-stack-tao-clean-architecture-react/)
- Kondov's caveat, in his own words: "**Software Design Must be Pragmatic**" — start with "a first draft" before adding structure; he warns against premature abstraction and against following design patterns rigidly. — [Kondov, 2024](https://alexkondov.com/full-stack-tao-clean-architecture-react/)
- The underlying pattern vocabulary is Fowler's, and Fowler himself insists the layers are only worth it if the domain is behaviour-rich: an Anemic Domain Model is "objects... connected with rich relationships and structure that true domain models have. The catch comes when you look at the behavior, and you realize that there is hardly any behavior on these objects, making them little more than bags of getters and setters." His verdict: "**The problem with anemic domain models is that they incur all of the costs of a domain model, without yielding any of the benefits.**" And on service layers: "Service layer advocates use a service layer in conjunction with a behaviorally rich domain model" — the service layer should be thin, with "all the key logic" in the domain. — [Martin Fowler, "AnemicDomainModel", 2003-11-25](https://martinfowler.com/bliki/AnemicDomainModel.html)

### Cited Findings — CRITICS
- The strongest *in-principle* objection found: Clean Architecture becomes harmful "when it treats React as an annoying detail to be hidden, since React isn't the domain but is a real part of the frontend model — rendering, interaction, cache coordination, forms, focus, and loading states all depend on the framework." — [Medium, "Clean Architecture for Frontend Sounds Smart — Until You Ship"](https://medium.com/@mernstackdevbykevin/clean-architecture-for-frontend-sounds-smart-until-you-ship-62f9ccf54030) — **authority: low (anonymous-ish Medium author); the argument is quotable, the source is not authoritative. Report writer should attribute it as "a common critique" rather than as an expert position.**
- Cost-of-change objection from the same critique: "every layer of abstraction adds friction, and adding a new field to a form shouldn't require updates to five different files and a schema migration"; full implementations "can make onboarding more difficult". — [Medium, ibid.](https://medium.com/@mernstackdevbykevin/clean-architecture-for-frontend-sounds-smart-until-you-ship-62f9ccf54030) — authority: low.
- The most *authoritative* critic-adjacent voice is Dan Abramov, arguing against abstraction-for-tidiness in general: "My code traded the ability to change requirements for reduced duplication, and it was not a good trade"; "Obsessing with 'clean code' and removing duplication is a phase many of us go through"; "**Clean code is not a goal. It's an attempt to make some sense out of immense complexity**"; "Let clean code guide you. **Then let it go.**" — [Dan Abramov, "Goodbye, Clean Code", overreacted.io, 2020-01-11](https://overreacted.io/goodbye-clean-code/) — note: this is about premature abstraction generally, **not** a direct rebuttal of Clean Architecture on the frontend; do not overstate it.
- A defence-of-Clean-Architecture rebuttal exists in the wider (backend) literature and is worth citing for balance: [threedots.tech, "Is Clean Architecture Overengineering?"](https://threedots.tech/episode/is-clean-architecture-overengineering/) — Go/backend focused; relevance to React is indirect.
- The *counter-consensus* that has actually won in practice: mainstream React architecture references (Bulletproof React, Wieruch) recommend **feature slices with unidirectional imports** and no domain layer at all — no `domain/`, `usecases/` or `ports/` folder appears in either recommended structure — [Bulletproof React](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md); [Robin Wieruch](https://www.robinwieruch.de/react-folder-structure/)
- Where the critics and advocates *agree*: use it when the app has non-trivial business logic, a team, and a long lifetime; avoid it for small apps, prototypes, and UI-only pages with no real business logic — [Bespoyasov, 2021](https://bespoyasov.me/blog/clean-architecture-on-frontend/); [Kondov, 2024](https://alexkondov.com/full-stack-tao-clean-architecture-react/); [Medium critique](https://medium.com/@mernstackdevbykevin/clean-architecture-for-frontend-sounds-smart-until-you-ship-62f9ccf54030)

### Inferences
- Fowler's anemic-domain-model argument cuts **against** most frontend Clean Architecture implementations rather than for them: a typical React "domain layer" is Zod schemas plus mapper functions — exactly "bags of getters and setters" with behaviour living in use-case services. By Fowler's own test that combination "incur[s] all of the costs of a domain model, without yielding any of the benefits."
- The real dividing line in the sources is not "layers: yes/no" but **where the invariants live**. When the server owns the invariants (the common SPA/BFF case), the frontend has no domain to model and a domain layer is ceremony. When the client owns genuine rules (offline-first apps, editors, CAD/design tools, pricing/configurator UIs, local simulation), the advocates' case is much stronger — and notably, TanStack's docs independently single out "design tools" as the case that still needs substantial client-owned synchronous state ([TanStack Query docs](https://tanstack.com/query/latest/docs/framework/react/guides/does-this-replace-client-state)).
- With RSC, an additional dilution argument applies: logic that would have justified a client domain layer can often move to the server component / server action, where a real domain layer already exists.

### Gaps
- I found **no** high-authority, named-expert article whose central thesis is "frontend apps should not have a domain layer." The critique circulates mainly on low-authority Medium/DEV posts and in comment threads. This asymmetry should be stated in the report: the advocacy side has better-credentialed writing than the opposition side, which lives in practice (what popular starters actually do) rather than in prose.
- No data found on adoption rates (what share of production React codebases use an explicit domain layer).

## Q5. Server state vs client state; TanStack Query, custom hooks over `useQuery`, key factories, and `select`

### Takeaway
The now-standard separation is **server state = a cached snapshot of data you don't own** (TanStack Query / RTK Query) vs **client state = data your app owns** (useState / reducer / Zustand). TkDodo's documented convention is a custom hook per query, colocated per feature, with query keys produced by a per-feature key factory; derived/transform logic has four possible homes and he ranks them with explicit trade-offs, placing `select` as the most capable but not unconditionally best.

### Cited Findings
- Official framing: TanStack Query is "a server-state library, responsible for managing asynchronous operations between your server and client", while Redux/MobX/Zustand are "client-state libraries" that can store async data "albeit inefficiently"; it "replaces the boilerplate code and related wiring used to manage cache data in your client-state" but is "**not a replacement for local/client state management**" — [TanStack Query docs, "Does this replace client state?"](https://tanstack.com/query/latest/docs/framework/react/guides/does-this-replace-client-state)
- Official: after moving async state out, most apps' truly-global client state ends up "very tiny"; apps with substantial synchronous client-only state (the docs name design tools) may still keep a traditional store alongside — [TanStack Query docs](https://tanstack.com/query/latest/docs/framework/react/guides/does-this-replace-client-state)
- Maintainer's reframing: "**React Query is an async state manager.** It can manage any form of asynchronous state — it is happy as long as it gets a Promise." — [TkDodo, "React Query as a State Manager", 2021-08-20](https://tkdodo.eu/blog/react-query-as-a-state-manager)
- Ownership argument behind the split: the frontend doesn't control the data it displays — "we only display a 'snapshot' of that data — the version of how it looked when we retrieved it", which is why the library "errs on the side of updating often rather than not updating often enough" — [TkDodo, 2021-08-20](https://tkdodo.eu/blog/react-query-as-a-state-manager)
- Custom-hook convention: even a thin wrapper around `useQuery` is worth it — "You can keep the actual data fetching out of the ui, but co-located with your `useQuery` call", keeping related logic in one place — [TkDodo, "Practical React Query", 2020-11-16 (upd. 2023-10-21)](https://tkdodo.eu/blog/practical-react-query)
- Query key = dependency array: "React Query will trigger a refetch whenever the query key changes" — so client state that parameterizes a request belongs in the key, replacing imperative `refetch()` orchestration — [TkDodo, "Practical React Query"](https://tkdodo.eu/blog/practical-react-query); reiterated in [TkDodo, "Effective React Query Keys"](https://tkdodo.eu/blog/effective-react-query-keys)
- Don't copy server state into client state: doing so means you "implicitly opt out of all background updates that React Query does for you, because the state 'copy' will not update with it" — [TkDodo, "Practical React Query"](https://tkdodo.eu/blog/practical-react-query)
- Cache-as-state-manager is out of bounds: "If you tamper with the queryCache (`queryClient.setQueryData`), it should only be for optimistic updates or for writing data that you receive from the backend after a mutation." — [TkDodo, "Practical React Query"](https://tkdodo.eu/blog/practical-react-query)
- Query key factory, per feature, generic → specific: `todoKeys = { all: ['todos'], lists: () => [...all,'list'], list: (filters) => [...lists(), {filters}], details: () => [...all,'detail'], detail: (id) => [...details(), id] }`; "Structure your Query Keys from *most generic* to *most specific*, with as many levels of granularity as you see fit"; "I keep my Query Keys next to their respective queries, co-located in a feature directory" (`src/features/Todos/queries.ts`), exporting only the hooks — [TkDodo, "Effective React Query Keys", 2021-06-13 (upd. 2022-04-23)](https://tkdodo.eu/blog/effective-react-query-keys)
- Where transformation logic goes — four options with documented trade-offs — [TkDodo, "React Query Data Transformations", 2021-03-10](https://tkdodo.eu/blog/react-query-data-transformations):
  - **On the backend**: pro "no work on the frontend"; con "not always possible".
  - **In the `queryFn`**: pro — close to backend logic; cons — "the transformed structure winds up in the cache, so you don't have access to the original structure", "runs on every fetch", and unfeasible when the API layer is shared/unmodifiable.
  - **In the render function**: pro — can be memoized; cons — "a bit more convoluted syntax", data may be `undefined` (optional chaining), "not recommended with tracked queries".
  - **With `select`**: pros — "best optimizations", "allows for partial subscriptions", selectors run only when data exists; cons — "Data structure can differ between observers" and "Structural sharing occurs twice".
- Anti-dogma from the same maintainer: "There is no free lunch. What might work in one situation might not work in others" — he cautions against embedding data-fetching in generically reusable components (e.g. a Button), and questions whether a container/presentational split always improves organization — [TkDodo, "React Query as a State Manager", 2021-08-20](https://tkdodo.eu/blog/react-query-as-a-state-manager)
- Redux's own docs now defer on this axis: "The single most common use case for side effects in a typical Redux app is fetching and caching data from the server. We recommend using RTK Query as the default approach for data fetching and caching in a Redux app." — [Redux Style Guide, Priority C](https://redux.js.org/style-guide/)

### Inferences
- The `select` vs hook vs component question has a defensible rule extractable from TkDodo's trade-offs: **normalization/shape-fixing belongs in the `queryFn`** (or the backend) because it should be cached; **view-specific derivation belongs in `select` inside a purpose-named hook** (`useTodosCount`) because it must not become the canonical cached shape; **nothing beyond formatting belongs in the component**. He does not state this rule in one sentence — it is an inference from the four-way comparison.
- The `select`-based partial-subscription argument is partly a re-render argument (out of scope per the constraints), but its *architectural* payload stands independently: `select` lets one cache entry serve several differently-shaped consumers, so per-view derivations need not fork the cache.
- "Query key as dependency array" is the mechanism that makes filter/sort/pagination *client* state the driver of *server* state without any orchestration layer — this is a large part of why frontend apps need less explicit application/use-case machinery than they did pre-2020.

### Gaps
- Full text of [TkDodo, "Thinking in React Query" (2023-06-07)](https://tkdodo.eu/blog/thinking-in-react-query) could not be extracted — the page is a slide/talk format and the fetch returned only the header. If the report needs his most recent synthesis (incl. his `staleTime` framing and "React Query is not a data fetching library"), that page must be read manually.

## Q6. Placement criteria: local state vs lifted vs context vs external store

### Takeaway
There is an explicit, official decision ladder: keep state local → lift it → extract components and pass `children` → only then context, and (per Redux's own guide and TanStack's) an external store only for state that is genuinely global, synchronous and client-owned. react.dev does list "managing state" as a legitimate context use case with a reducer, which is in tension with the popular "context is not a state manager" slogan — the slogan's real content is mostly a re-render argument (out of scope) plus a genuine architectural point about unavailability outside the React tree.

### Cited Findings
- Official ladder, verbatim: "**Just because you need to pass some props several levels deep doesn't mean you should put that information into context.**" Consider first: (1) "Start by passing props... it makes it very clear which components use which data! The person maintaining your code will be glad you've made the data flow explicit with props." (2) "Extract components and pass JSX as `children` to them... If you pass some data through many layers of intermediate components that don't use that data... this often means that you forgot to extract some components along the way." Then: "If neither of these approaches works well for you, consider context." — [react.dev, "Passing Data Deeply with Context"](https://react.dev/learn/passing-data-deeply-with-context)
- Official warning: "Context is very tempting to use, but **it's too easy to overuse it.** The key is to exhaust simpler alternatives (explicit props and component extraction) before reaching for context." — [react.dev, "Passing Data Deeply with Context"](https://react.dev/learn/passing-data-deeply-with-context)
- Official sanctioned use cases for context: theming, current account, routing, and — explicitly — "**Managing state**: As your app grows, you might end up with a lot of state closer to the top of your app. Many distant components below may want to change it. It is common to use a reducer together with context to manage complex state and pass it down to distant components without too much hassle." — [react.dev, "Passing Data Deeply with Context"](https://react.dev/learn/passing-data-deeply-with-context)
- Official reducer+context recipe and its logic-placement payoff: "Reducers let you consolidate a component's state update logic. Context lets you pass information deep down to other components. You can combine reducers and context together to manage state of a complex screen." Docs recommend wrapping consumption in custom hooks (`useTasks()`, `useTasksDispatch()`) so that "all of the context and reducer wiring is in `TasksContext.js`. This keeps the components clean and uncluttered, focused on what they display rather than where they get the data." And: "You can have many context-reducer pairs like this in your app... a powerful way to scale your app and lift state up without too much work." — [react.dev, "Scaling Up with Reducer and Context"](https://react.dev/learn/scaling-up-with-reducer-and-context)
- Expert colocation rule: "**Keep state as close to where it's needed as possible**"; "Not everything in your application needs to be in a single state object" — different logical concerns get their own providers at the appropriate tree level (user settings and notifications need not share a context). Also endorses putting update logic inside the provider's custom hook: "what's cool about this approach is that we could put all the logic for common ways to update the state in our `useCount` hook" — which lets you swap `useState` for `useReducer` internally without touching consumers. — [Kent C. Dodds, "Application State Management with React", 2020-07-21](https://kentcdodds.com/blog/application-state-management-with-react)
- Redux's own placement rule: "**Evaluate Where Each Piece of State Should Live**" — "Values that are 'local' should generally be kept in the nearest UI component instead." — [Redux Style Guide](https://redux.js.org/style-guide/)
- Redux: read granularly rather than centrally — "Prefer having more UI components subscribed to the Redux store and reading data at a more granular level", and "prefer calling `useSelector` many times and retrieving smaller amounts of data, instead of having a single larger `useSelector` call" — [Redux Style Guide](https://redux.js.org/style-guide/)
- The "context is not a state manager" argument, in its strongest architectural form: context is a **dependency-injection** mechanism — it lets you store, read and subscribe to a value, but "updating a value is non-existent", and "Context does not give any option to access its data outside the React tree, whereas Redux and other State Management libraries do" — [Test Double, "Using React Context for dependency injection, not state management"](https://testdouble.com/insights/react-context-for-dependency-injection-not-state-management); [DEV, "React Context Is Not State Management"](https://dev.to/nainikmehta/react-context-is-not-state-management-stop-using-it-4i3l) — **authority: community consensus / low-to-medium; the re-render half of this argument is out of scope here.**
- Related maintainer nuance: TanStack Query + React Context is itself discussed as a DI/scoping tool by TkDodo — [TkDodo, "React Query and React Context"](https://tkdodo.eu/blog/react-query-and-react-context)
- After server state is delegated to a query library, truly-global client state is "very tiny" for most apps — the practical criterion for whether Zustand/Redux/Jotai is needed at all — [TanStack Query docs](https://tanstack.com/query/latest/docs/framework/react/guides/does-this-replace-client-state)

### Inferences
- The sources do **not** actually conflict as much as the slogan suggests. react.dev endorses context + reducer for state *distribution* of app-level state; the "not a state manager" camp objects to context *as the store's update engine and as the only access path*. Both agree that consumers should read through a purpose-named custom hook, never `useContext(RawContext)` scattered in components.
- A defensible synthesized ladder (inference, not a quote from any single source): local `useState` → `useReducer` when updates have rules → lift → `children` composition → context+reducer per concern (react.dev) → external store only when state must be (a) written from outside React, (b) read outside the React tree, or (c) shared across unrelated trees. Only (a)-(c) are documented *architectural* reasons rather than performance reasons.
- No source retrieved distinguishes Zustand vs Jotai vs Redux on *architectural* grounds (atomic vs single-store); that choice appears to be treated as ergonomics, not architecture.

### Gaps
- No official react.dev statement exists on when to adopt an external store; the closest official-adjacent statements are Redux's own style guide and TanStack's docs, both of which have a vested interest.
- No authoritative (maintainer-level) source found for the Zustand/Jotai placement criteria specifically.

## Q7. Forms and validation: schema shared with the server, or component-level?

### Takeaway
The 2025-2026 convention is a **schema-first, shared-schema** approach: one Zod schema used by both the client form and the server action/endpoint, with form *state* kept local (never in the global store). React 19's `useActionState` + Server Actions make the server the authoritative validator while the same schema gives instant client feedback. Sources on this are mostly community-level; the strongest hard rule available is Redux's.

### Cited Findings
- Hard rule, official (Redux): "**Avoid Putting Form State In Redux** — Most form state shouldn't go in Redux. In most use cases, the data is not truly global, is not being cached, and is not being used by multiple components at once. Prefer keeping the form edits themselves in local component state, and only dispatching an action to update the Redux store once the user has completed the form." — [Redux Style Guide](https://redux.js.org/style-guide/)
- Official (react.dev) on event-driven logic, which forms are the canonical case of: "You don't need Effects to handle user events... In the Buy button click event handler, you know exactly what happened. By the time an Effect runs, you don't know *what* the user did... This is why you'll usually handle user events in the corresponding event handlers." — [react.dev, "You Might Not Need an Effect"](https://react.dev/learn/you-might-not-need-an-effect)
- React 19 mechanism: `useActionState` (imported from `react`) pairs with Server Actions and returns "the current action state — including any errors your action returned", so validation results flow back into the UI without client-side state plumbing — [Next.js docs, "How to Create Forms with Server Actions"](https://nextjs.org/docs/app/guides/forms)
- Shared-schema guidance: "you can use a schema validation library like Zod or Valibot to validate the form fields" server-side; the recommended shape is a single Zod schema imported by both client and server, avoiding duplicated rules, with `useActionState` rendering the errors — [Next.js docs, "Forms with Server Actions"](https://nextjs.org/docs/app/guides/forms); [Robin Wieruch, "Next.js Forms with Server Actions", 2026](https://www.robinwieruch.de/next-forms/)
- Hybrid pattern (client-side RHF + server action, one schema): documented by a recognized practitioner — [Markus Oberlehner, "Using react-hook-form with React 19, useActionState, and Next.js 15 App Router"](https://markus.oberlehner.net/blog/using-react-hook-form-with-react-19-use-action-state-and-next-js-15-app-router)
- Discipline point: prefer `safeParse` over `parse` in handlers — "Never use `.parse()` directly in API route handlers. If the input is invalid it throws an unhandled exception. Use `.safeParse()` and return a 400 response explicitly." — [community synthesis via search of Zod validation practice](https://www.wisp.blog/blog/validating-api-response-with-zod) — **authority: community; treat as practice, not doctrine.**
- Type derivation rule that makes a shared schema viable as the contract: derive the TS type with `z.infer<typeof Schema>` rather than hand-writing a parallel type — [DEV, "Runtime Validation in TypeScript: Where Zod Ends..."](https://dev.to/gabrielanhaia/runtime-validation-in-typescript-where-zod-ends-and-the-type-system-begins-4e9e)

### Inferences
- The shared Zod schema is the clearest *real-world* example of a frontend "domain artifact" that is genuinely framework-independent, testable outside React, and reusable on the server — i.e. the pragmatic 90% substitute for a domain layer (ties to Q4).
- Trust boundary, implied by all sources but stated by none in one line: client-side validation is UX, server-side validation is correctness; sharing the schema removes the duplication without collapsing the boundary.

### Gaps
- No official react.dev page states where validation logic should live; React 19 form docs cover mechanism (`useActionState`, `useFormStatus`, actions), not placement policy.
- No authoritative source found comparing "validate in the component" vs "validate in the schema" head-to-head; schema-first is assumed by every source retrieved.

## Q8. Named anti-patterns

### Takeaway
Four are documented at authoritative level: **Effect-as-data-fetching** and **Effect-as-derived-state** (react.dev, with specific failure modes), **prop drilling** (react.dev, but framed as a *reason to extract components*, not automatically a reason for context), and **lifecycle-wrapper hooks** (`useMount`/`useEffectOnce`/`useUpdateEffect`, react.dev). "Fat component" and "god hook" are real community terms but lack authoritative definitions.

### Cited Findings
- **Effect for derived state** — "🔴 Avoid: redundant state and unnecessary Effect" (`setFullName` in an Effect) vs "✅ Good: calculated during rendering". Rule: "To avoid the unnecessary render passes, **transform all the data at the top level of your components**. That code will automatically re-run whenever your props or state change." — [react.dev, "You Might Not Need an Effect"](https://react.dev/learn/you-might-not-need-an-effect)
- **Effect for user events** — see Q7 quote; logic belongs in the event handler because only the handler knows what happened — [react.dev, "You Might Not Need an Effect"](https://react.dev/learn/you-might-not-need-an-effect)
- **Effect as the data-fetching mechanism** — permitted but discouraged: "Keep in mind that modern frameworks provide more efficient built-in data fetching mechanisms than writing Effects directly in your components." Documented failure mode is the race condition: typing "hello" fast produces fetches for "h","he","hel","hell","hello" with "no guarantee about which order the responses will arrive in"; the fix requires an `ignore` flag in cleanup. "These issues apply to any UI library, not just React. Solving them is not trivial, which is why modern frameworks provide more efficient built-in data fetching mechanisms than fetching data in Effects." — [react.dev, "You Might Not Need an Effect"](https://react.dev/learn/you-might-not-need-an-effect)
- Official escape hatch when you must fetch in an Effect: "If you don't use a framework (and don't want to build your own) but would like to make data fetching from Effects more ergonomic, consider extracting your fetching logic into a custom Hook" (`useData(url)`); "In general, whenever you have to resort to writing Effects, keep an eye out for when you can extract a piece of functionality into a custom Hook with a more declarative and purpose-built API like `useData`." — [react.dev, "You Might Not Need an Effect"](https://react.dev/learn/you-might-not-need-an-effect)
- **RSC alternative to Effect-fetching** (React 19 era): "With Server Components, you can read the data and render it in the component" — the docs contrast a client `useEffect(() => fetch('/api/notes/'+id)...)` against `async function Note({id}) { const note = await db.notes.get(id); ... }`, citing elimination of client-server waterfalls and not shipping heavy libraries to the client; interactivity is added by composing with Client Components via `"use client"` — [react.dev, "Server Components"](https://react.dev/reference/rsc/server-components)
- **Lifecycle-wrapper hooks** — "🔴 `useMount(fn)`, `useEffectOnce(fn)`, `useUpdateEffect(fn)`"; "Custom 'lifecycle' Hooks like `useMount` don't fit well into the React paradigm." — [react.dev, "Reusing Logic with Custom Hooks"](https://react.dev/learn/reusing-logic-with-custom-hooks)
- **Prop drilling** — named in official docs as the problem context+reducer solves ("without the repetitive 'prop drilling'"), while the context page insists the first remedy is usually missing component extraction, not context — [react.dev, "Scaling Up with Reducer and Context"](https://react.dev/learn/scaling-up-with-reducer-and-context); [react.dev, "Passing Data Deeply with Context"](https://react.dev/learn/passing-data-deeply-with-context)
- **Logic-in-the-dispatcher (Redux-specific "fat handler")** — "Wherever possible, try to put as much of the logic for calculating a new state into the appropriate reducer, rather than in the code that prepares and dispatches the action (like a click handler)", because "Putting logic in reducers means you know where to look for the update logic, instead of having it scattered in random other parts of the application code" — [Redux Style Guide](https://redux.js.org/style-guide/)
- **Setter-shaped actions** — "We recommend trying to treat actions more as 'describing events that occurred', rather than 'setters'"; `{type:'food/orderAdded'}` over `{type:'orders/setPizzasOrdered'}`; and "Minimize the use of 'blind spreads/returns' like `return action.payload`... the reducer effectively gives up its ownership of what that state looks like." — [Redux Style Guide](https://redux.js.org/style-guide/)
- **Complex logic inside components** (Redux, generalizable): "We still encourage moving complex synchronous or async logic outside components, usually into thunks. This is especially true if the logic needs to read from the store state." Plus: reducers must be pure — "They must not execute any kind of asynchronous logic (AJAX calls, timeouts, promises), generate random values (`Date.now()`, `Math.random()`), modify variables outside the reducer..." — [Redux Style Guide](https://redux.js.org/style-guide/)
- **Copying server state into local state** (the query-era anti-pattern) — you "implicitly opt out of all background updates" — [TkDodo, "Practical React Query"](https://tkdodo.eu/blog/practical-react-query); and **using the query cache as a client store** — `setQueryData` only for optimistic updates or post-mutation server data — [ibid.](https://tkdodo.eu/blog/practical-react-query)
- **Fat / god components** — community term: "The 'God Component' anti-pattern results in a massive, fragile component that requires 20 different boolean flags to render correctly" — [DEV, "Stop God Components: React Composition Patterns"](https://dev.to/iprajapatiparesh/stop-god-components-react-composition-patterns-31e4) — authority: low/community. The nearest expert-level statement is Kondov's "Pulling all the logic in a few components leads to bloat" and "If a part of the markup is complex, requires loops and conditionals — extract it." — [Alex Kondov, "Tao of React"](https://alexkondov.com/tao-of-react/)
- **God hook / over-extraction** — community framing: hooks "turn into invisible containers of state, side effects, and assumptions that are no longer obvious at the call site"; also "Unnecessary custom hooks and premature abstraction can lead to over-engineering" — [Medium, "Custom React Hooks Are Overused"](https://medium.com/@rahulkengale1110/custom-hooks-are-making-your-react-code-worse-and-most-developers-dont-realize-it-540579277248); [techinsights.manisuec.com, "React Hooks Anti-Patterns"](https://techinsights.manisuec.com/reactjs/react-hooks-antipatterns/) — authority: low. The authoritative substitute is react.dev's positive rule ("Keep custom Hooks focused on concrete high-level use cases", "constraining what it does") plus Abramov's general warning against premature abstraction — [react.dev](https://react.dev/learn/reusing-logic-with-custom-hooks); [overreacted.io, "Goodbye, Clean Code"](https://overreacted.io/goodbye-clean-code/)
- **HOCs as the logic-sharing mechanism** — **[SUPERSEDED]** by hooks: "Hooks have proven to be the most efficient way to achieve such composition", and they let components "clearly track value sources without prop confusion" — [Alex Kondov, "Tao of React"](https://alexkondov.com/tao-of-react/)

### Inferences
- The strongest single anti-pattern claim available is compositional: `useEffect` + `fetch` + `useState` in a component simultaneously violates three documented rules (Effect-for-fetching, derived-state-in-Effect, and logic-not-extracted-to-a-hook) — which is why "you might not need an Effect" has become the de-facto architectural test for where logic sits.
- "Fat component" and "god hook" should be presented in the final report as *folk terms with no authoritative definition*, backed by react.dev's positive rules rather than by the blog posts that name them.

### Gaps
- No authoritative source defines a size/complexity threshold for components or hooks (no official "max lines", "max hooks per component" guidance was found).

### Explicitly marked as superseded
- **Container/Presentational as a mandated split** — superseded by custom Hooks (2019, by its own author) — https://medium.com/@dan_abramov/smart-and-dumb-components-7ca2f9a7c7d0
- **HOCs / render props as the primary logic-sharing mechanism** — superseded by hooks — https://alexkondov.com/tao-of-react/
- **`useEffect` + `fetch` as the app's data-fetching layer** — superseded by framework data fetching, RSC, or a query cache — https://react.dev/learn/you-might-not-need-an-effect and https://react.dev/reference/rsc/server-components
- **Redux as the place to put server data** — superseded by RTK Query / TanStack Query, per Redux's own style guide — https://redux.js.org/style-guide/
- **Fowler's Anemic Domain Model critique (2003)** — still valid as a pattern argument, but written for server-side OO systems; applies to frontend only by analogy — https://martinfowler.com/bliki/AnemicDomainModel.html

### Where sources genuinely disagree (do not smooth over)
- **Domain layer, yes or no.** Bespoyasov and Kondov argue for explicit layers with inward dependencies; Bulletproof React and Wieruch — the two most-followed structural references — recommend feature slices with *no* domain/use-case/ports layer at all; the loudest opposition is low-authority. The honest summary is: *advocacy is better written, rejection is better adopted.*
- **Context as a state manager.** react.dev lists "Managing state" (context + reducer) as a legitimate use case; the "context is not a state manager" camp (Test Double and many others) says context is dependency injection and cannot serve as a store. Partly a terminological clash, partly a real disagreement about whether state should be reachable outside the React tree.
- **Where derived logic lives with TanStack Query.** TkDodo gives four legitimate homes with trade-offs and explicitly refuses to rank them universally ("There is no free lunch"); anyone claiming a single correct answer is going beyond the source.
- **Whether RSC restores container/presentational.** Rivosecchi says the shape reappears but warns the naive version defeats RSC's purpose; react.dev describes the server/client boundary without invoking the old pattern at all.
