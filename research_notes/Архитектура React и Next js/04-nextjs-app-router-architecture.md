## 1. RSC boundary: where `"use client"` goes, and what the boundary actually means

### Takeaway
`"use client"` marks the **entry point of a client subtree in the module graph**, not a single component:
every module the marked file *imports* joins the client bundle, but Server Components passed in as
`children`/props do **not**, because they are never imported — only their rendered output crosses. The
official guidance is therefore to put the directive on the smallest interactive leaf (or on a thin
wrapper) rather than high in the tree.

### Cited Findings
- `"use client"` "is used to declare a **boundary** between the Server and Client module graphs (trees)." — [Server and Client Components, nextjs.org docs (v16.3.7, lastUpdated 2026-08-25)](https://nextjs.org/docs/app/getting-started/server-and-client-components)
- "Once a file is marked with `"use client"`, **all of its imports and the components it directly renders are included in the client bundle**. This means you don't need to add the directive to every component that is intended for the client." — [Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)
- The subtree rule is scoped to the *module graph*: "This behavior applies to components that are part of the Client Component's module graph, which includes the modules it imports and the components it renders directly. **It does not apply to Server Components passed as children or other props.** Those components are not imported into the Client Component's module graph. They are rendered on the server and passed to the Client Component as rendered output." — [Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)
- The "push to the leaves" guidance is phrased by Vercel as a bundle-size instruction, not an architecture law: "add `'use client'` to specific interactive components instead of marking large parts of your UI as Client Components." The worked example keeps `<Layout>` a Server Component with `<Logo />` (server) and only `<Search />` marked client. — [Server and Client Components §Reducing JS bundle size](https://nextjs.org/docs/app/getting-started/server-and-client-components)
- Two-rule formulation of the boundary: "**Code** crosses through imports. Whatever a Client Component imports is pulled into the client bundle. **Data** crosses through props, and it must be serializable, so functions like event handlers cannot cross." — [The Server and Client Boundary, nextjs.org docs (lastUpdated 2026-08-25)](https://nextjs.org/docs/app/guides/server-and-client-boundary)
- "You only need `'use client'` at the entry to a client subtree, not on every file inside it. Every module imported from that entry becomes part of the client module graph." — [Server and Client Boundary](https://nextjs.org/docs/app/guides/server-and-client-boundary)
- Recommended escape hatch for shared components: "To leave a shared component unchanged, create a Client Component wrapper that imports it and place the directive on the wrapper. The wrapper keeps the shared module unchanged and **puts the boundary closer to your application code**." — [Server and Client Boundary](https://nextjs.org/docs/app/guides/server-and-client-boundary)
- The `children` composition workaround, verbatim pattern: "A common pattern is to use `children` to create a *slot* in a `<ClientComponent>`." Server `Page` renders `<Modal><Cart /></Modal>`; `Modal` is `"use client"`, `Cart` stays a Server Component. "In this pattern, Server Components are rendered on the server ahead of time, even when passed as props to Client Components." — [Server and Client Components §Interleaving](https://nextjs.org/docs/app/getting-started/server-and-client-components)
- Why it works, in React ownership terms: "The **owner** is the component whose source contains the JSX for a child… The **parent** directly contains the child in the rendered tree. Because `Cart`'s owner is a Server Component, `Cart` renders on the server. `Modal` is only the parent, so `Modal` receives `Cart`'s output to place but not its code to run." — [Server and Client Boundary](https://nextjs.org/docs/app/guides/server-and-client-boundary)
- "A rendered React element can cross the boundary because it is serializable data." Any prop works, not just `children` — the docs example passes `title={<div>Your cart</div>}` alongside `children`. — [Server and Client Boundary](https://nextjs.org/docs/app/guides/server-and-client-boundary)
- Context is a boundary artifact: "React context is not supported in Server Components." The fix is a `"use client"` provider that accepts `children`, imported by a server `layout`. Explicit placement guidance: "**You should render providers as deep as possible in the tree** – notice how `ThemeProvider` only wraps `{children}` instead of the entire `<html>` document." — [Server and Client Components §Context providers](https://nextjs.org/docs/app/getting-started/server-and-client-components)
- A Client Component runs in **both** environments, which is an architectural constraint people miss. Docs table: Server Component = "on the server: Yes / in the browser: No"; Client Component = "on the server: Yes / in the browser: Yes". "The word 'Client' indicates that a Client Component also runs in the browser, **alongside its server render**." — [Server and Client Boundary §Rendering environments](https://nextjs.org/docs/app/guides/server-and-client-boundary)
- Third-party libraries without the directive: wrap them. "If you're building a component library, add the `"use client"` directive to entry points that rely on client-only features." — [Server and Client Components §Third-party components](https://nextjs.org/docs/app/getting-started/server-and-client-components)
- Known breakage at the boundary: compound components. "A Server Component that imports a Client Component receives a client reference instead of the function. As a result, `Menu.Item` is `undefined`, and React throws 'Element type is invalid.' … To use its pieces from a Server Component, expose them as **named exports** instead of static properties." — [Server and Client Boundary](https://nextjs.org/docs/app/guides/server-and-client-boundary)

### Inferences
- "Push client components to the leaves" is, in the current docs, justified primarily by bundle size, and only secondarily by architecture. The architectural payoff the docs actually lean on is *access*: only a Server Component can read secrets/DB/`server-only` modules, so pushing the boundary down is what preserves a server-side data layer at all.
- The `children`-slot pattern is the single most load-bearing composition primitive in App Router architecture: it is what lets a stateful client shell (modal, tabs, accordion, provider) wrap server-rendered content without dragging that content's code — and its imports, including DB clients — into the browser bundle.
- Because a Client Component still renders on the server, `"use client"` is **not** an opt-out of SSR. Opting out requires `next/dynamic` with `ssr: false` (see §7).

### Gaps
- react.dev's own `"use client"` reference page was not fetched directly (call budget). Its wording on serialization and on the directive's placement rules is cited here only via the Next.js docs' links to it (`react.dev/reference/rsc/use-client`, `react.dev/reference/react/use-server#serializable-parameters-and-return-values`). The report-writer should treat the react.dev text as unverified-verbatim.

## 2. What can and cannot cross the boundary; `server-only` / `client-only`

### Takeaway
Props from server → client must be **serializable by React**; functions and classes are blocked by
default, with one exception (a `'use server'` Server Function, which crosses as a *reference*). The
`server-only` / `client-only` packages are build-time poka-yoke: they turn "accidentally imported
server code into the client graph" from a runtime leak into a build error, and Next.js implements
them internally rather than using the npm packages' contents.

### Cited Findings
- "Props passed to Client Components need to be **serializable** by React." — [Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)
- "Passing a function as a prop from a Server Component to a Client Component **throws**. An event handler like `onClick` cannot cross. A Server Function marked with `'use server'` crosses as a reference." — [Server and Client Boundary](https://nextjs.org/docs/app/guides/server-and-client-boundary)
- TypeScript cannot distinguish the two, so Next.js ships a naming heuristic: "A Server Function is not distinguishable from a plain function by its type. The TypeScript plugin allows a Client Component prop typed as a function **when its name is `action` or ends in `Action`**. The plugin flags other function props." — [Server and Client Boundary](https://nextjs.org/docs/app/guides/server-and-client-boundary)
- "Functions and classes are already blocked from being passed to Client Components by default." — [How to think about data security in Next.js (lastUpdated 2026-08-25)](https://nextjs.org/docs/app/guides/data-security)
- Class instances are used *deliberately* as a leak guard in the official DAL example: "Use classes to avoid accidentally passing the whole object to the client" — `getCurrentUser()` returns `new User(decodedToken.id)`. — [Data security §Data Access Layer](https://nextjs.org/docs/app/guides/data-security)
- Rendered React elements cross fine (they are serializable data) — see §1.
- `server-only`: import `'server-only'` into a module and "if you try to import the module into a Client Component, there will be a **build-time error**." `client-only` is "the corresponding package … to mark modules that contain client-only logic like code that accesses the `window` object." — [Server and Client Components §Preventing environment poisoning](https://nextjs.org/docs/app/getting-started/server-and-client-components)
- Installation is optional and the packages are hollow: "In Next.js, installing `server-only` or `client-only` is **optional**… Next.js handles `server-only` and `client-only` imports internally to provide clearer error messages when a module is used in the wrong environment. **The contents of these packages from NPM are not used by Next.js.**" Next.js also ships its own type declarations for them, for `noUncheckedSideEffectImports`. — [Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)
- Env vars are the other half of the guard: "only environment variables prefixed with `NEXT_PUBLIC_` are included in the client bundle. If variables are not prefixed, Next.js replaces them with an empty string." Consequence: a leaked `getData()` "can be imported and executed on the client, [but] it won't work as expected" — a silent failure, which is why `server-only` is recommended on top. — [Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)
- Additional defence-in-depth layer, still experimental: React Taint APIs `experimental_taintObjectReference` (objects) and `experimental_taintUniqueValue` (values), enabled via `experimental.taint` in `next.config.js`. Docs qualify it: "it's an additional layer of protection, you should **still** filter and sanitize the data in your DAL before passing it to React's render context." — [Data security §Tainting](https://nextjs.org/docs/app/guides/data-security)
- Client Components are held to browser-grade trust even during the server render: "[Client Components] Run on the server during prerendering, but **must follow the same security assumptions as code running in the browser**. Must not access privileged data or server-only modules." — [Data security §Passing data from server to client](https://nextjs.org/docs/app/guides/data-security)

### Inferences
- The `action`/`*Action` naming convention is not cosmetic: it is the only mechanism by which the type system distinguishes a legal Server Function prop from an illegal event-handler prop. Codebases that pass server functions under other prop names will be flagged by the Next.js TS plugin.
- `server-only` is the architectural enforcement mechanism for a data layer. Without it, "the data layer lives on the server" is a convention; with it, it is a compile error. This is the cheapest possible guardrail for a `lib/`-or-`data/`-based DAL.

### Gaps
- The docs never enumerate the exact serializable set (Date, `Map`/`Set`, `BigInt`, symbols, `URL`, typed arrays…). They defer to react.dev's `use-server#serializable-parameters-and-return-values`, which was not fetched. Do **not** state a definitive allow-list from these notes.

## 3. File conventions and their architectural roles

### Takeaway
`app/` is a filesystem router where **folders define URL segments** and a segment becomes publicly
reachable only when it contains `page` or `route`. Every other convention is a *boundary* the router
installs for you: `layout` = persistent shell, `template` = non-persistent shell, `error`/`global-error`
= React error boundaries, `loading` = Suspense boundary, `not-found` = "not found" error boundary,
`default` = parallel-slot fallback, plus purely organizational `(group)` / `_private` folders and
`@slot` / `(.)intercept` for slot and overlay UI.

### Cited Findings — the routing files
Docs table, verbatim roles ("Add `page` to expose a route, `layout` for shared UI such as header, nav,
or footer, `loading` for skeletons, `error` for error boundaries, and `route` for APIs"):
| File | Extensions | Documented role |
|---|---|---|
| `layout` | `.js .jsx .tsx` | Layout |
| `page` | `.js .jsx .tsx` | Page |
| `loading` | `.js .jsx .tsx` | Loading UI |
| `not-found` | `.js .jsx .tsx` | Not found UI |
| `error` | `.js .jsx .tsx` | Error UI |
| `global-error` | `.js .jsx .tsx` | Global error UI |
| `route` | `.js .ts` | API endpoint |
| `template` | `.js .jsx .tsx` | **Re-rendered layout** |
| `default` | `.js .jsx .tsx` | **Parallel route fallback page** |
— [Project structure and organization, nextjs.org docs (v16.3.7, lastUpdated 2026-07-21)](https://nextjs.org/docs/app/getting-started/project-structure)

- Nesting semantics: "Folders define URL segments. Nesting folders nests segments. **Layouts at any level wrap their child segments. A route becomes public when a `page` or `route` file exists.**" — [Project structure](https://nextjs.org/docs/app/getting-started/project-structure)
- The composition order is fixed and is the architectural contract for where boundaries sit: `layout.js` → `template.js` → `error.js` (React error boundary) → `loading.js` (React suspense boundary) → `not-found.js` (React error boundary for "not found" UI) → `page.js` or nested `layout.js`; "rendered recursively in nested routes." — [Project structure §Component hierarchy](https://nextjs.org/docs/app/getting-started/project-structure)
- Dynamic segments: `[segment]` single param, `[...segment]` catch-all, `[[...segment]]` optional catch-all; "Access values via the `params` prop." — [Project structure §Dynamic routes](https://nextjs.org/docs/app/getting-started/project-structure)
- Route groups `(folder)`: "This indicates the folder is for organizational purposes and should **not be included** in the route's URL path." Useful for "organizing routes by site section, intent, or team," for "enabling nested layouts in the same route segment level," including **multiple root layouts** — "remove the top-level `layout.js` file, and add a `layout.js` file inside each route group… The `<html>` and `<body>` tags need to be added to each root layout." Also the documented trick for scoping a `loading.tsx` to one page without changing the URL. — [Project structure §Route groups](https://nextjs.org/docs/app/getting-started/project-structure)
- Private folders `_folder`: "prefixing a folder with an underscore… indicates the folder is a private implementation detail and should not be considered by the routing system, thereby **opting the folder and all its subfolders** out of routing." Escape hatch: "You can create URL segments that start with an underscore by prefixing the folder name with `%5F`." — [Project structure §Private folders](https://nextjs.org/docs/app/getting-started/project-structure)
- Parallel + intercepting routes, verbatim table: `@folder` = "Named slot" (sidebar + main content); `(.)folder` = "Intercept same level" (preview sibling route in a modal); `(..)folder` = "Intercept parent"; `(..)(..)folder` = "Intercept two levels"; `(...)folder` = "Intercept from root." Framing: "These features fit specific UI patterns, such as slot-based layouts or modal routing… render another route inside the current layout **without changing the URL**." — [Project structure §Parallel and Intercepted Routes](https://nextjs.org/docs/app/getting-started/project-structure)
- Parallel slots render **whether or not they are displayed**: "The rendering work is split into chunks, by individual route segments (layouts and pages), **including parallel route slots whether or not they are displayed**." (Security-relevant; see §5.) — [Server and Client Components §On the server](https://nextjs.org/docs/app/getting-started/server-and-client-components)
- Top-level folders: `app` (App Router), `pages` (**Pages Router — legacy**), `public`, optional `src`. Top-level files now include `proxy.ts` ("Next.js request proxy"), `instrumentation.ts`, `next.config.js`, `next-env.d.ts`. **`middleware.ts` is absent from the current table.** — [Project structure §Top-level files](https://nextjs.org/docs/app/getting-started/project-structure)
- Metadata file conventions are also route files: `favicon`/`icon`/`apple-icon`, `opengraph-image`/`twitter-image`, `sitemap.(xml|ts)`, `robots.(txt|ts)` — the code variants are effectively specialized route handlers. — [Project structure §Metadata file conventions](https://nextjs.org/docs/app/getting-started/project-structure)

### Inferences
- `template.tsx` vs `layout.tsx` is a **state-lifetime** decision, not a styling one: a layout instance persists across navigations within its segment (which is exactly why auth checks in layouts are unsafe — §5), while a template remounts. Any per-navigation effect, animation-on-enter, or resettable form state belongs in `template`.
- `default.tsx` only matters once parallel routes exist; it is the "what does this slot show on a hard navigation where the slot's state is unknown" answer. A codebase with no `@slot` folders needs no `default.tsx`.
- `global-error.tsx` is the only error boundary above the root layout, so it must render its own `<html>`/`<body>`; it is the last-resort shell, not a general error page.

### Gaps
- `forbidden.tsx` / `unauthorized.tsx` (introduced Next 15.1 alongside `forbidden()` / `unauthorized()`) are **not listed** in the current Project-structure routing-files table I fetched, and `mdx-components.tsx` is not in the top-level files table either. I did not fetch their API-reference pages, so I cannot state their current status. Do not assert either way.
- `middleware.ts`: I have strong indirect evidence it is renamed to `proxy.ts` (absent from the top-level table; the Authentication and Backend-for-Frontend guides now write `proxy.ts` / `export default async function proxy(req)` and note "Third-party libraries may still refer to `proxy` as `middleware`"). I did **not** fetch a migration/changelog page stating the rename and its version. Flag as high-confidence-but-unconfirmed provenance.

## 4. Colocation: `app/_components` vs `src/components`

### Takeaway
Next.js's official position is explicitly **unopinionated**: colocation inside `app/` is safe because a
folder is not routable without `page`/`route`, private `_folders` are an *optional* convention on top of
that, and the docs present three equally-valid layouts (everything outside `app/`, everything in
top-level folders inside `app/`, or split by feature/route) with the instruction to pick one and be
consistent.

### Cited Findings
- "Next.js is **unopinionated** about how you organize and colocate your project files." — [Project structure §Organizing your project](https://nextjs.org/docs/app/getting-started/project-structure)
- The safety mechanism: "a route is **not publicly accessible** until a `page.js` or `route.js` file is added to a route segment… And, even when a route is made publicly accessible, only the **content returned** by `page.js` or `route.js` is sent to the client. This means that **project files** can be **safely colocated** inside route segments in the `app` directory without accidentally being routable." — [Project structure §Colocation](https://nextjs.org/docs/app/getting-started/project-structure)
- Private folders are convenience, not necessity: "Since files in the `app` directory can be safely colocated by default, **private folders are not required for colocation.** However, they can be useful for: separating UI logic from routing logic; consistently organizing internal files across a project and the Next.js ecosystem; sorting and grouping files in code editors; **avoiding potential naming conflicts with future Next.js file conventions.**" — [Project structure §Private folders](https://nextjs.org/docs/app/getting-started/project-structure)
- The `_components` / `_lib` convention is shown in the official table: `app/blog/_components/Post.tsx` → "Not routable; safe place for UI utilities"; `app/blog/_lib/data.ts` → "Not routable; safe place for utils." — [Project structure §Route groups and private folders](https://nextjs.org/docs/app/getting-started/project-structure)
- Warning for teams that skip private folders: "If you don't use private folders, it would be helpful to know Next.js special file conventions to prevent unexpected naming conflicts." — [Project structure](https://nextjs.org/docs/app/getting-started/project-structure)
- The three sanctioned strategies, verbatim headings: **"Store project files outside of `app`"** ("keeps the `app` directory purely for routing purposes"); **"Store project files in top-level folders inside of `app`"**; **"Split project files by feature or route"** ("stores globally shared application code in the root `app` directory and **splits** more specific application code into the route segments that use them"). Framed as "a very high-level overview of common strategies. **The simplest takeaway is to choose a strategy that works for you and your team and be consistent across the project.**" — [Project structure §Examples](https://nextjs.org/docs/app/getting-started/project-structure)
- Folder names carry no framework meaning: "we're using `components` and `lib` folders as generalized placeholders, **their naming has no special framework significance** and your projects might use other folders like `ui`, `utils`, `hooks`, `styles`, etc." — [Project structure](https://nextjs.org/docs/app/getting-started/project-structure)
- `src/` is orthogonal and purely cosmetic: "Next.js supports storing application code (including `app`) inside an optional `src` folder. This separates application code from project configuration files which mostly live in the root of a project." — [Project structure §`src` folder](https://nextjs.org/docs/app/getting-started/project-structure)

### Inferences
- There is no official recommendation to choose `app/_components` **over** `src/components`; they are the "split by feature/route" and "outside of `app`" strategies respectively, and the docs rank neither. Any source claiming Next.js *recommends* one is over-reading.
- The one genuinely technical argument for `_folder` is forward-compat: an underscore is the only guarantee that a future Next.js file convention (a new `tests.tsx`, say) cannot collide with your colocated file. That is a real, if small, architectural reason to prefer `_components` inside `app/`.
- Colocated tests are covered by the same rule — a `page.test.tsx` next to `page.tsx` is not routable — but the docs never say the word "tests." Treat "official position on colocating tests" as an inference from the general colocation rule, not a quotation.

### Gaps
- No official statement specifically about test files, stories, or fixtures inside `app/`. The colocation rule implies safety; the docs do not endorse or discourage the practice.

## 5. Data layer placement: the DAL, `server-only` guards, and where authorization belongs

### Takeaway
Next.js now documents **three** data-access architectures and tells you to pick exactly one: external
HTTP APIs (for existing orgs with a separate backend), a dedicated **Data Access Layer** (recommended
for new projects), or component-level queries (prototypes only). Authorization belongs **as close as
possible to the data source** — inside the DAL — and explicitly **not** in `proxy`/middleware (optimistic
checks only) and **not** in layouts (they don't re-render on navigation and don't gate their siblings).

### Cited Findings — the three approaches
- "There are three main approaches we recommend for fetching data in Next.js, depending on the size and age of your project: **HTTP APIs**: for existing large applications and organizations. **Data Access Layer**: for new projects. **Component-Level Data Access**: for prototypes and learning." And: "**We recommend choosing one data fetching approach and avoiding mixing them.** This makes it clear for both developers working in your code base and security auditors what to expect." — [How to think about data security in Next.js (lastUpdated 2026-08-25)](https://nextjs.org/docs/app/guides/data-security)
- The external-API approach is first-class, not a fallback: "You should follow a **Zero Trust** model when adopting Server Components in an existing project. You can continue calling your existing API endpoints such as REST or GraphQL from Server Components using `fetch`, just as you would in Client Components." It "works well when: You already have security practices in place. **Separate backend teams use other languages or manage APIs independently.**" — [Data security §External HTTP APIs](https://nextjs.org/docs/app/guides/data-security)
- DAL definition: "For new projects, we recommend creating a dedicated **Data Access Layer (DAL)**. This is an internal library that controls how and when data is fetched, and what gets passed to your render context. A Data Access Layer should: **Only run on the server. Perform authorization checks. Return safe, minimal Data Transfer Objects (DTOs).**" — [Data security §Data Access Layer](https://nextjs.org/docs/app/guides/data-security)
- Secrets are scoped to the DAL: "Secret keys should be stored in environment variables, but **only the Data Access Layer should access `process.env`**. This keeps secrets from being exposed to other parts of the application." — [Data security](https://nextjs.org/docs/app/guides/data-security)
- Canonical file layout in the docs: `data/auth.ts` (`getCurrentUser` wrapped in React `cache`), `data/user-dto.tsx` (starts with `import 'server-only'`), consumed from `app/page.tsx`. In the Authentication guide the same idea lives at `app/lib/dal.ts` with `verifySession()` + `getUser()`, and `app/lib/dto.ts`. — [Data security](https://nextjs.org/docs/app/guides/data-security); [How to implement authentication in Next.js (lastUpdated 2026-08-25)](https://nextjs.org/docs/app/guides/authentication)
- `React.cache` is part of the pattern, and the stated reason is *architectural*, not perf: "Cached helper methods makes it easy to get the same value in many places without manually passing it around. **This discourages passing it from Server Component to Server Component which minimizes risk of passing it to a Client Component.**" — [Data security](https://nextjs.org/docs/app/guides/data-security)
- Component-level access is named as the anti-pattern with a labelled `// EXPOSED:` code comment: passing a raw `userData` row into a `"use client"` `<Profile user={userData} />` "exposes all the fields in userData to the client." The `BAD` props-interface comment: "it accepts way more data than the Client Component needs and **it encourages server components to pass all that data down.**" — [Data security §Component-level data access](https://nextjs.org/docs/app/guides/data-security)
- DTO rationale: "return only the necessary data that will be used in your application, and not entire objects… rather than the entire user object which could contain passwords, phone numbers, etc." — [Authentication §Using Data Transfer Objects](https://nextjs.org/docs/app/guides/authentication)

### Cited Findings — where authorization belongs (post-CVE-2025-29927 posture)
- The headline rule: "While Proxy can be useful for initial checks, **it should not be your only line of defense in protecting your data. The majority of security checks should be performed as close as possible to your data source**, see Data Access Layer." — [Authentication §Optimistic checks with Proxy (Optional)](https://nextjs.org/docs/app/guides/authentication)
- Proxy/middleware is restricted to *optimistic* checks by design: "since Proxy runs on every route, including prefetched routes, it's important to **only read the session from the cookie (optimistic checks), and avoid database checks**." Its legitimate uses are "to centralize redirect logic and pre-filter unauthorized users" and "to protect static routes that share data between users (e.g. content behind a paywall)." — [Authentication](https://nextjs.org/docs/app/guides/authentication)
- Two-tier taxonomy: "**Optimistic**: … using the session data stored in the cookie… useful for quick operations, such as showing/hiding UI elements or redirecting users. **Secure**: … using the session data stored in the database… used for operations that require access to sensitive data or actions." For both, the docs recommend a DAL + DTOs, with Proxy as optional. — [Authentication §Authorization](https://nextjs.org/docs/app/guides/authentication)
- Layouts are explicitly **not** an authorization boundary — two independent reasons: (a) "be cautious when doing checks in Layouts as these **don't re-render on navigation**, meaning the user session won't be checked on every route change"; (b) "**A layout also does not control whether the rest of the route renders.** Route segments and parallel route slots are rendered by the router, so a layout that hides or swaps them does not stop them from running or from appearing in the RSC Payload." Conclusion: "Instead, you should do the checks close to your data source or the component that'll be conditionally rendered." — [Authentication §Layouts and auth checks](https://nextjs.org/docs/app/guides/authentication)
- The SPA habit is named and rejected: "A common pattern in SPAs is to `return null` in a layout or a top-level component if a user is not authorized. **This pattern is not recommended** since Next.js applications have multiple entry points, which will not prevent nested route segments and Server Actions from being accessed." — [Authentication](https://nextjs.org/docs/app/guides/authentication)
- Why DAL-level checks beat page-level checks: putting the check inside `getUser()` "guarantees that wherever `getUser()` is called within your application, the auth check is performed, and **prevents developers from forgetting to check** that the user is authorized to access the data." — [Authentication](https://nextjs.org/docs/app/guides/authentication)
- Client Components cannot participate: "**Client Components can't import the DAL.** Run `verifySession()`, `getUser()`, or similar in a parent Server Component, then pass data to client children as props or through a context provider." — [Authentication §Auth and streaming](https://nextjs.org/docs/app/guides/authentication)
- Never trust URL/segment input: `params` and `searchParams` are user input. "**BAD: Trusting searchParams directly**" → `isAdmin === 'true'` → "Vulnerable: relies on untrusted client data"; "**GOOD: Re-verify every time**" from the cookie. Audit checklist adds: "**`/[param]/`** Folders with brackets are user input. Are params validated?" — [Data security](https://nextjs.org/docs/app/guides/data-security)
- The official audit checklist (useful as an architecture review rubric): established isolated DAL with DB packages and env vars not imported outside it; `"use client"` files' props not expecting private data; `"use server"` files validating args, re-authorizing, checking resource ownership, filtering return values, delegating DB access to a `server-only` DAL; bracketed params validated; "**`proxy.ts` and `route.ts`: Have a lot of power. Spend extra time auditing these using traditional techniques.**" — [Data security §Auditing](https://nextjs.org/docs/app/guides/data-security)
- DAL applies to writes too: "Just as we recommend a Data Access Layer for reading data, you can apply the same pattern to mutations. This keeps authentication, authorization, and database logic in a dedicated `server-only` module, while `"use server"` actions stay thin." Example: `data/posts.ts` (`import 'server-only'`, auth + ownership + delete) and `app/actions.ts` (`deletePostAction` → calls DAL → `revalidatePath`). — [Data security §Using a Data Access Layer for mutations](https://nextjs.org/docs/app/guides/data-security)
- Static-route caveat on the DAL: "A DAL can be used to protect data fetched at request time. However, for static routes that share data between users, data will be fetched **at build time** and not at request time. Use Proxy to protect static routes." — [Authentication](https://nextjs.org/docs/app/guides/authentication)

### Cited Findings — CVE-2025-29927 (the middleware bypass that motivates the above)
> ⚠️ Sourced from **search-result summaries** of credible security vendors, not full-page fetches. Treat
> the specific numbers as corroborated-but-not-verbatim-verified.
- Disclosed **2025-03-21**, CVSS **9.1**, credited to researcher Rachid Allam. Affects Next.js before **12.3.5, 13.5.9, 14.2.25, 15.2.3**. — [Snyk: CVE-2025-29927 Authorization Bypass in Next.js Middleware](https://snyk.io/blog/cve-2025-29927-authorization-bypass-in-next-js-middleware/); [Datadog Security Labs: Understanding CVE-2025-29927](https://securitylabs.datadoghq.com/articles/nextjs-middleware-auth-bypass/); [JFrog: CVE-2025-29927 Authorization Bypass in Next.js](https://jfrog.com/blog/cve-2025-29927-next-js-authorization-bypass/)
- Mechanism: Next.js trusted an internal `x-middleware-subrequest` header (used to prevent infinite middleware loops). `runMiddleware` split the header on `:` and compared against `middlewareInfo.name`; on a match the request **skipped middleware entirely**, including auth. Exploit is a single header: `x-middleware-subrequest: middleware`. — [ProjectDiscovery: technical analysis](https://projectdiscovery.io/blog/nextjs-middleware-authorization-bypass); [Zscaler ThreatLabz](https://www.zscaler.com/blogs/security-research/cve-2025-29927-next-js-middleware-authorization-bypass-flaw)
- Mitigations: upgrade, or block external requests carrying `x-middleware-subrequest` at the edge. — [OffSec](https://www.offsec.com/blog/cve-2025-29927/); [Picus Security](https://www.picussecurity.com/resource/blog/cve-2025-29927-nextjs-middleware-bypass-vulnerability)
- **Second, later RSC-protocol CVE worth flagging:** CVE-2025-55182 ("React2Shell"), disclosed **December 2025**, CVSS **10.0**, pre-auth RCE in React Server Components' Server-Functions request handling (server-side prototype pollution → `child_process.execSync`). Reported fixed in Next.js 15.0.5 / 15.1.9 / 15.2.6 / 15.3.6 / 15.4.8 / 15.5.7 / 16.0.7 and React 19.0.1 / 19.1.2 / 19.2.1. — [Akamai security research](https://www.akamai.com/blog/security-research/cve-2025-55182-react-nextjs-server-functions-deserialization-rce); [Datadog Security Labs](https://securitylabs.datadoghq.com/articles/cve-2025-55182-react2shell-remote-code-execution-react-server-components/); [Vercel changelog: Summary of CVE-2025-55182](https://vercel.com/changelog/cve-2025-55182); [Qualys](https://blog.qualys.com/product-tech/2025/12/10/react2shell-decoding-cve-2025-55182-the-silent-threat-in-react-server-components)

### Inferences
- CVE-2025-29927 did not *create* the "don't authorize in middleware" guidance — the Authentication guide's optimistic/secure split predates it — but it converted that guidance from a performance note into a security requirement, and the current docs now phrase it as a hard rule with a named alternative (the DAL). The rename to `proxy.ts` reinforces the reframing: the file is a *proxy*, not a security gate.
- For a project that already has a separate backend API (e.g. a Fastify service), the officially sanctioned architecture is **"External HTTP APIs" + Zero Trust**, not a Next-side DAL. Authorization then lives in that backend, and the Next app must not be the place it is enforced. The docs' "choose one and don't mix" instruction argues against adding a partial Next-side DAL on top.
- The layout non-boundary fact is the single most under-appreciated architectural constraint in App Router: it rules out the entire React-SPA habit of "guard the whole subtree in one place."

- No official Next.js/Vercel postmortem page for CVE-2025-29927 was fetched; I cannot quote Vercel's own words on it or pin which doc paragraphs were added in response.
- CVE-2025-55182 details (exact CVSS, affected list) come from vendor summaries via search; the Vercel changelog URL is listed but not fetched.

## 6. Server Actions vs Route Handlers vs a separate API

### Takeaway
Server Actions are the **mutation** primitive and are public, unauthenticated HTTP POST endpoints until
you authorize inside them; Route Handlers are the **public API-layer** primitive for non-UI responses,
webhooks, callbacks and proxying. Next.js explicitly says its backend features "are not a full backend
replacement," and explicitly tells Server Components **not** to fetch through your own Route Handlers.

### Cited Findings — Server Actions
- Role: "Server Actions let you run server-side code from the client. **Their primary purpose is to mutate data from your frontend client.** Server Actions are queued. **Using them for data fetching introduces sequential execution.**" — [How to use Next.js as a backend for your frontend (lastUpdated 2026-06-25)](https://nextjs.org/docs/app/guides/backend-for-frontend)
- They are public endpoints: "By default, when a Server Action is created and exported, it is **reachable via a direct POST request, not just through your application's UI.** This means, even if a Server Action or utility function is not imported elsewhere in your code, it can still be called externally." — [Data security](https://nextjs.org/docs/app/guides/data-security)
- Built-in mitigations, and their explicit limits: **secure action IDs** ("encrypted, non-deterministic IDs… periodically recalculated between builds"; "created during compilation and are cached for a maximum of 14 days") and **dead-code elimination** of unused actions. "This security improvement reduces the risk in cases where an authentication layer is missing. However, **you should still treat Server Actions as reachable via direct POST requests and verify authentication and authorization inside each one.**" — [Data security](https://nextjs.org/docs/app/guides/data-security)
- Page-level auth does not protect actions: "**A page-level authentication check does not extend to the Server Actions defined within it. Always re-verify inside the action.**" The doc's own annotation: "The page-level redirect on line 6 controls which UI is rendered, but **the Server Action is a separate entry point and must verify the caller on its own.**" — [Data security §Authentication and authorization](https://nextjs.org/docs/app/guides/data-security)
- Authorization ≠ authentication: "Beyond authentication (is the user logged in?), remember to check **authorization** (does this user have permission to act on this specific resource?). This prevents Insecure Direct Object Reference (IDOR) vulnerabilities." — [Data security](https://nextjs.org/docs/app/guides/data-security)
- "Treat Server Actions with the same security considerations as **public-facing API endpoints**." — [Authentication §Server Actions](https://nextjs.org/docs/app/guides/authentication)
- Return values are a leak surface: "Server Action return values are serialized and sent to the client. **Only return what the UI needs, not raw database records.**" — [Data security §Controlling return values](https://nextjs.org/docs/app/guides/data-security)
- Closures over sensitive values are encrypted, "**but we don't recommend relying on encryption alone**"; a new private key is generated per action per build, so "actions can only be invoked for a specific build," and multi-server self-hosting needs `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`. — [Data security §Closures and encryption](https://nextjs.org/docs/app/guides/data-security)
- CSRF posture: POST-only, plus `Origin` vs `Host`/`X-Forwarded-Host` comparison; reverse-proxy/multi-layer setups need `serverActions.allowedOrigins`. — [Data security §Allowed origins](https://nextjs.org/docs/app/guides/data-security)
- Mutations must never be render side-effects: "Next.js explicitly prevents setting cookies or triggering cache revalidation within render methods"; a `searchParams.logout` → `cookies.delete()` in a page body is labelled BAD. — [Data security §Avoiding side-effects during rendering](https://nextjs.org/docs/app/guides/data-security)

### Cited Findings — Route Handlers
- Framing and the explicit limit: Next.js supports the "Backend for Frontend" pattern, but "**Next.js backend capabilities are not a full backend replacement.** They serve as an API layer that: is publicly reachable; handles any HTTP request; can return any content type." — [Backend for Frontend](https://nextjs.org/docs/app/guides/backend-for-frontend)
- "Route Handlers are **public HTTP endpoints. Any client can access them.** … To restrict access, implement authentication and authorization." And: "Treat Route Handlers with the same security considerations as public-facing API endpoints." — [Backend for Frontend](https://nextjs.org/docs/app/guides/backend-for-frontend); [Authentication §Route Handlers](https://nextjs.org/docs/app/guides/authentication)
- Documented *good* uses: non-UI content types (JSON/XML/images/files/text, `rss.xml`, `llms.txt`, `.well-known`); content negotiation via `Accept`-header rewrites; consuming request payloads; data manipulation/aggregation ("keeps logic out of the frontend and **avoids exposing internal systems**"); **proxying to another backend** with validation before forwarding; **webhooks** (e.g. CMS-triggered `revalidateTag`); **callback URLs** (OAuth-style, setting an httpOnly cookie then redirecting); CORS preflight (`OPTIONS` auto-added if undefined).— [Backend for Frontend](https://nextjs.org/docs/app/guides/backend-for-frontend)
- The anti-pattern, stated as a hard caveat: "**Fetch data in Server Components directly from its source, not via Route Handlers.** For Server Components prerendered at build time, using Route Handlers **will fail the build step**… For Server Components rendered on demand, fetching from Route Handlers is slower due to the extra HTTP round trip between the handler and the render process." — [Backend for Frontend §Caveats](https://nextjs.org/docs/app/guides/backend-for-frontend)
- When client-side fetching *is* endorsed, and what to use: "Server Components cover most data-fetching needs. However, fetching data client side might be necessary for: Data that depends on client-only Web APIs (Geo-location, Storage, Audio, File); **Frequently polled data.** For these, use community libraries like `swr` or `react-query`." — [Backend for Frontend §Caveats](https://nextjs.org/docs/app/guides/backend-for-frontend)
- Deployment constraints that shape whether a Route Handler is even viable: "Some hosts deploy Route Handlers as lambda functions… cannot share data between requests; the environment may not support writing to File System; long-running handlers may be terminated due to timeouts; **WebSockets won't work**." — [Backend for Frontend](https://nextjs.org/docs/app/guides/backend-for-frontend)
- `output: 'export'` mode: "only `GET` Route Handlers are supported, in combination with the `dynamic` route segment config, set to `'force-static'`." — [Backend for Frontend](https://nextjs.org/docs/app/guides/backend-for-frontend)
- Proxy is not an auth layer here either: "Always verify credentials before granting access. **Do not rely on proxy alone for authentication and authorization.**" — [Backend for Frontend §Security](https://nextjs.org/docs/app/guides/backend-for-frontend)
- Next 15 shipped both Server Action hardening items as release features: "Even if a Server Action or utility function is not imported elsewhere in your code, **it's still a publicly accessible HTTP endpoint.** … **You should still treat Server Actions as public HTTP endpoints.**" — [Next.js 15 blog, Delba de Oliveira, Jimmy Lai, Rich Haines, 2024-10-21](https://nextjs.org/blog/next-15)

### Inferences
- Decision rule the docs support: **mutation from your own UI → Server Action** (thin, delegating to a `server-only` DAL); **anything a third party or non-browser client must call, or any non-HTML content type → Route Handler**; **reads inside Server Components → call the source directly**, never your own `app/api/*`.
- When a separate backend API already exists, `app/api/*/route.ts` is **redundant for data reads** (both the Server-Component path and the browser-TanStack-Query path can hit the real API) and remains justified only for: webhooks/callbacks that must land on the web origin, hiding a credential the browser must not hold, same-origin cookie handling / CORS avoidance, and response reshaping. Route Handlers in that setting are a BFF, not the API.
- Server Actions and a separate backend API are not mutually exclusive, but a Server Action that merely forwards to the backend adds a hop and a second authorization surface that must be secured independently — a real architectural cost, given "a page-level authentication check does not extend to the Server Actions defined within it."

### Gaps
- The docs do not publish a side-by-side "Server Action vs Route Handler vs external API" decision table; the rule above is assembled from scattered caveats.

## 7. SPECIAL CASE: the "SPA-in-App-Router" pattern (every `page.tsx` is `"use client"`, `useParams()`, TanStack Query against a separate backend, only the root layout server-side)

### Takeaway
Next.js **officially and explicitly supports building SPAs** with the App Router, and every individual
ingredient of this pattern is documented and sanctioned (`useParams` is a Client hook; TanStack Query
is a named, first-class option with its own official guide page; external HTTP APIs are one of three
recommended data-access architectures). But the official SPA guide's *recommended* patterns all still
begin in a Server Component — so "every `page.tsx` is `"use client"`" is a **valid but un-endorsed
degenerate case**, not the documented SPA architecture. I found **no official page that recommends,
names, or evaluates** the all-client-pages variant.

### Cited Findings — official support for SPAs
- Official guide exists and states support unambiguously. Title: "How to build single-page applications with Next.js"; description: "**Next.js fully supports building Single-Page Applications (SPAs).**" — [Single-Page Applications guide, nextjs.org (v16.3.7, lastUpdated 2026-08-25)](https://nextjs.org/docs/app/guides/single-page-applications)
- Definition it works against: "a 'strict SPA' … **Client-side rendering (CSR)**: The app is served by one HTML file… Every route, page transition, and data fetch is handled by JavaScript in the browser. **No full-page reloads**." And a critique of that baseline: "Strict SPAs often require large amounts of JavaScript to load before the page can be interactive. Further, **client data waterfalls can be challenging to manage.**" — [SPA guide](https://nextjs.org/docs/app/guides/single-page-applications)
- The incremental-adoption pitch: "Next.js can start as a static site or **even a strict SPA where everything is rendered client-side.** If your project grows, you can progressively add more server features (e.g. React Server Components, Server Actions, and more) as needed." — [SPA guide](https://nextjs.org/docs/app/guides/single-page-applications)
- What the guide's five documented SPA patterns actually are: (1) React `use` inside a Context Provider — **fetch in a Server Component (root layout), pass the un-awaited Promise down**; (2) browser-only components via `next/dynamic` `{ ssr: false }`; (3) shallow routing with native `window.history.pushState`/`replaceState`, which "integrate into the Next.js Router, allowing you to sync with `usePathname` and `useSearchParams`"; (4) mutations via Server Actions + `useTransition`/`useOptimistic`/`useActionState`/`useFormStatus`; (5) optional `output: 'export'` static export. Companion demo: `next-spa-patterns.labs.vercel.dev` / [vercel-labs/next-spa-patterns](https://github.com/vercel-labs/next-spa-patterns). — [SPA guide](https://nextjs.org/docs/app/guides/single-page-applications)
- Note that pattern (1) is the **opposite** of all-client-pages: "Start the request in a Server Component (here, the root layout) **without awaiting it**, and pass the Promise to the provider… Starting the request on the server, before the rest of the app renders, lets the response stream immediately and **avoids client-side request waterfalls**." — [SPA guide](https://nextjs.org/docs/app/guides/single-page-applications)
- Migration paths are first-class: guides exist for [from Create React App](https://nextjs.org/docs/app/guides/migrating/from-create-react-app) and [from Vite](https://nextjs.org/docs/app/guides/migrating/from-vite). — [SPA guide](https://nextjs.org/docs/app/guides/single-page-applications)

### Cited Findings — the individual ingredients
- `useParams` is sanctioned: "`useParams` is a **Client Component hook** that lets you read a route's dynamic params filled in by the current URL." Returns `string | string[]` per segment; `{}` when the route has no dynamic params; **in Pages Router it "will return `null` on the initial render"** (legacy caveat). Introduced v13.3.0. — [useParams API reference (v16.3.6, lastUpdated 2026-06-09)](https://nextjs.org/docs/app/api-reference/functions/use-params)
- **Cost of `useParams` under Cache Components:** "When `cacheComponents` is enabled, `useParams` may require a `Suspense` boundary… **Routes with dynamic params not covered by `generateStaticParams`**: the param is not known until request time. **`useParams` suspends. Wrap the component (or a parent) in a `Suspense` boundary … otherwise, the build fails.**" — [useParams API reference](https://nextjs.org/docs/app/api-reference/functions/use-params)
- TanStack Query is officially documented, with its own guide page and a pattern table: `useQuery` (inline loading), `useSuspenseQuery` (Suspense loading), `<HydrationBoundary>` (data provided by the server); SWR's equivalents are `useSWR`, `useSWR` + `suspense: true`, `<SWRConfig fallback>`. — [Client-side data fetching (lastUpdated 2026-08-25)](https://nextjs.org/docs/app/guides/client-side-data-fetching); sub-page [TanStack Query](https://nextjs.org/docs/app/guides/client-side-data-fetching/tanstack-query)
- When a client library is warranted: "Use a client data-fetching library such as SWR, TanStack Query, or Apollo Client when Client Components need a **shared browser cache**. These libraries can add focus revalidation, interval polling, request deduplication, or optimistic updates across components." Counterweight: "**Many apps can provide responsive interactions without a client data-fetching library.** If a Client Component only needs to read server data once, pass it a Promise and unwrap it with React's `use()`… This avoids adding a library for data that never revalidates on the client." — [Client-side data fetching](https://nextjs.org/docs/app/guides/client-side-data-fetching)
- Fetching from a separate backend is an officially recommended architecture: see §5, "External HTTP APIs: for existing large applications and organizations… Separate backend teams use other languages or manage APIs independently." — [Data security](https://nextjs.org/docs/app/guides/data-security)
- Up to three cache layers can coexist and must be reconciled by hand: Next.js server cache (`cacheLife` revalidate/expire), Next.js client cache (RSC payloads, `cacheLife` stale), and the client library's own cache (SWR key / TanStack query key). "The cache layers keep independent freshness policies and do not need matching durations. **Cache identities and mutation invalidation must stay coordinated across layers.**" — [Client-side data fetching](https://nextjs.org/docs/app/guides/client-side-data-fetching)

### Cited Findings — what the all-client variant costs (each cost is individually documented)
- `"use client"` does **not** disable SSR: "Client components are **prerendered** during `next build`." Disabling it requires `next/dynamic` with `{ ssr: false }` per component. So all-client pages are still rendered twice (server prerender + browser hydration) unless explicitly opted out. — [SPA guide §Rendering components only in the browser](https://nextjs.org/docs/app/guides/server-and-client-boundary) / [SPA guide](https://nextjs.org/docs/app/guides/single-page-applications)
- Losing the server graph means losing the officially recommended data layer: "**Client Components can't import the DAL.**" And Client Components "must not access privileged data or server-only modules." — [Authentication §Auth and streaming](https://nextjs.org/docs/app/guides/authentication); [Data security](https://nextjs.org/docs/app/guides/data-security)
- The SPA-idiomatic auth guard is explicitly rejected: "A common pattern in SPAs is to `return null` in a layout or a top-level component if a user is not authorized. **This pattern is not recommended** since Next.js applications have multiple entry points." — [Authentication](https://nextjs.org/docs/app/guides/authentication)
- SEO/crawler consequence stated as architecture, not perf: "A crawler that reads only HTML sees the first response and runs none of your JavaScript… **SEO depends on whether the server render reaches the content.** Content gated behind user interaction or an event does not appear in the HTML available to a crawler that does not run JavaScript." — [Server and Client Boundary](https://nextjs.org/docs/app/guides/server-and-client-boundary)
- A `params` Promise is still the documented server-side way to read route params (`const { id } = await params`), and `useParams()` is its client-side counterpart — both exist; neither is deprecated. — [Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components); [useParams](https://nextjs.org/docs/app/api-reference/functions/use-params)
- Static export as the honest end-state of an all-client app: `output: 'export'` produces an `out/` folder of HTML/CSS/JS, but "**Next.js server features are not supported with static exports.**" The docs argue static export beats a strict SPA because you get "an HTML file per route" and "fully rendered pages for each route" instead of "a minimal skeleton for all routes." — [SPA guide §Static export](https://nextjs.org/docs/app/guides/single-page-applications)

### Inferences
- **Verdict on the pattern:** it is *supported and valid*, not *recommended*. Nothing in the docs forbids `"use client"` on every page, `useParams()` instead of `await params`, or TanStack Query against an external API — each is individually documented. What the docs never do is present that combination as an architecture; every SPA pattern they *do* present retains a Server Component parent as the place where the first request starts.
- Concretely, what such a project gives up: (a) the DAL and `server-only` enforcement (authorization must live entirely in the separate backend — which is fine, and is exactly the "External HTTP APIs / Zero Trust" approach); (b) server-side streaming of first data via `use()` → hence client request waterfalls, the specific problem the SPA guide names; (c) HTML-visible content for non-JS crawlers; (d) secret access in page code. What it keeps: file-system routing, `next/link` prefetching + URL-persisted routing state, per-route code splitting, layouts, error/loading boundaries.
- It also inherits a maintenance hazard: `useParams` is documented to **suspend and fail the build** under `cacheComponents` for dynamic params not covered by `generateStaticParams`. An all-client-pages app that reads params via `useParams()` is therefore coupled to keeping `cacheComponents` off, or to wrapping every such page in `<Suspense>`. Reading params via the `params` prop does not carry that specific caveat.
- The root-layout-only-server-component arrangement is actually the *exact shape* the SPA guide's flagship pattern assumes (it fetches in `app/layout.tsx` and passes a Promise into a client provider) — so this project's structure is one small step away from the officially recommended SPA architecture, without abandoning the client-side data layer.

### Gaps
- **No official Next.js/Vercel page discusses "mark every `page.tsx` as `use client`" by name**, nor rates it, nor lists its tradeoffs as a named pattern. I searched and fetched the SPA guide, the client-side data-fetching guide and the boundary guide; none of them name it. This is a genuine documentation void, and the report should say so rather than imply an official position exists.
- I did not find a Lee Robinson / Delba de Oliveira / Vercel-engineer blog post specifically addressing the all-client-pages App Router variant. Absence of evidence here, not evidence of absence — my call budget ran out.
- I did not verify whether any Next.js lint rule or build warning fires for a `"use client"` page.

## 8. Next.js 15 breaking changes with architectural impact (and their 2026 status)

### Takeaway
Two Next 15 changes reshape architecture rather than performance: request-scoped APIs (`cookies`,
`headers`, `draftMode`, `params`, `searchParams`) became **Promises**, and caching defaults flipped from
cached to **uncached** for `GET` Route Handlers and the Client Router Cache. Both are still in force in
2026, layered under the newer Cache Components model.

### Cited Findings
- Async Request APIs (breaking): "we are transitioning APIs that rely on request-specific data—such as `headers`, `cookies`, `params`, and `searchParams`—to be **asynchronous**." Affected list: `cookies`, `headers`, `draftMode`, `params` in `layout.js`, `page.js`, `route.js`, `default.js`, `generateMetadata`, `generateViewport`, and `searchParams` in `page.js`. Codemod: `npx @next/codemod@canary next-async-request-api .`. — [Next.js 15, 2024-10-21, Delba de Oliveira / Jimmy Lai / Rich Haines](https://nextjs.org/blog/next-15)
- Stated *reason* is architectural, not perf-first: "not all components depend on request-specific data, so it's unnecessary to wait for the request to render them… **To enable this, and set the stage for future optimizations, we need to know when to wait for the request.**" — [Next.js 15](https://nextjs.org/blog/next-15)
- Caching semantics (breaking): "**`fetch` requests, `GET` Route Handlers, and client navigations are no longer cached by default.**" Rationale given: "we re-evaluated our caching heuristics and how they would interact with projects like Partial Prerendering (PPR) and with third party libraries using `fetch`." — [Next.js 15](https://nextjs.org/blog/next-15)
- `GET` Route Handlers: "In Next 14, Route Handlers that used the `GET` HTTP method were cached by default unless they used a dynamic function or dynamic config option. In Next.js 15, `GET` functions are **not cached by default**." Opt back in with `export dynamic = 'force-static'`. Metadata route files (`sitemap.ts`, `opengraph-image.tsx`, `icon.tsx`) "remain static by default." — [Next.js 15](https://nextjs.org/blog/next-15)
- Client Router Cache: default `staleTime` of `0` for Page segments; "as you navigate around your app, the client will always reflect the latest data from the Page component(s)". Unchanged: shared layout data is not refetched (partial rendering preserved), back/forward restores from cache, `loading.js` stays cached 5 minutes. Opt out via `experimental.staleTimes.dynamic`. — [Next.js 15](https://nextjs.org/blog/next-15)
- React 19: "In version 15, the App Router uses React 19 RC, and we've also introduced backwards compatibility for React 18 with the **Pages Router**" — i.e. React 18 on Pages Router is a legacy accommodation, not an App Router option. "While it is possible to run the Pages Router on React 18 and the App Router on React 19 in the same application, **we don't recommend this setup.**" — [Next.js 15](https://nextjs.org/blog/next-15)
- Other Next 15 breaking changes with architectural bearing: `revalidateTag`/`revalidatePath` during render now **throw**; `ssr: false` with `next/dynamic` is **disallowed in Server Components**; `runtime = "experimental-edge"` deprecated in favour of `"edge"`; `force-dynamic` now sets a `no-store` default on the fetch cache. — [Next.js 15](https://nextjs.org/blog/next-15)
- Server Actions security shipped as a Next 15 feature: unguessable action IDs + dead-code elimination of unused actions. — [Next.js 15](https://nextjs.org/blog/next-15)
- **2026 status:** the Next 15 async-params model persists in current docs (`const { id } = await params`, `const cookieStore = await cookies()`), and caching has since been reorganized under an opt-in **Cache Components** model (`cacheComponents` in `next.config.js`, `cacheLife`, `updateTag`, `revalidateTag(tag, 'max')`, and a dedicated "Caching without Cache Components" doc). — [Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components); [Client-side data fetching](https://nextjs.org/docs/app/guides/client-side-data-fetching); [useParams](https://nextjs.org/docs/app/api-reference/functions/use-params)

### Inferences
- Async `params`/`searchParams` is what makes the `params`-prop vs `useParams()` choice non-trivial: the server path now costs an `await` inside an async component, which is why client-heavy codebases drift toward `useParams()`. Both are current; the choice is about where the data layer lives, not about API availability.
- The uncached-by-default flip removed the main reason to route reads through `app/api/*` for cheap caching, reinforcing §6's "don't fetch your own Route Handlers from Server Components."

### Gaps
- I did not fetch a Next.js 16 release blog post, so I cannot enumerate Next 16's own breaking changes, date the `middleware.ts` → `proxy.ts` rename, or say when Cache Components became the documented default path. **Flag this as the largest version gap in these notes.**

## 9. Dissent: credible critiques of App Router architecture

### Takeaway
There is substantive, named engineering dissent — not just "it's hard." The strongest documented
criticisms are architectural: RSC forces interactive UI to be split across files/graphs, every soft
navigation must reach the Next.js server regardless of what the client already holds, and page content
is transmitted twice (HTML + RSC payload). These directly contradict Vercel's framing of the same
features as simplifications.

### Cited Findings
- Clover Caruso (2025-10-21), on composition: "**Components rendered by the React Server, by design, can not be modified after mounting**," which forces splitting server data-fetching from client interactivity across files; the author notes "nearly every piece of UI displays some dynamic data," yet the framework's grain discourages that. — [One Year with Next.js App Router — Why We're Moving On, Clover Caruso, paperclover.net, 2025-10-21](https://paperclover.net/blog/webdev/one-year-next-app-router)
- Same source, on navigation: "**a navigation to a new page _has_ to fetch the Next.js server, regardless of what data the client already has available!**" — demonstrated by returning to `/` after visiting `/other` and seeing a re-fetch. — [paperclover.net](https://paperclover.net/blog/webdev/one-year-next-app-router)
- Same source, on double transmission: Server Components require sending page markup twice — as HTML for first paint and again as an RSC payload in JSON-quoted JavaScript — which "**doubles the size of the initial HTML payload**" and is "fundamentally unavoidable within RSC architecture." *(Listed here because it is an architectural consequence of the RSC protocol, not a tuning issue.)* — [paperclover.net](https://paperclover.net/blog/webdev/one-year-next-app-router)
- Same source, outcome: the team migrated to **TanStack Start**, incrementally via Vite config aliases, and reports "the site performed faster from every angle: Development Mode, Production page load times, Soft navigations, and at a lower price." — [paperclover.net](https://paperclover.net/blog/webdev/one-year-next-app-router)
- The post was discussed at length on Hacker News (useful for the counter-arguments the report may want): [HN item 45755911](https://news.ycombinator.com/item?id=45755911); mirrored on [devtalk.com](https://devtalk.com/t/one-year-with-next-js-app-router-and-why-were-moving-on/220751)
- A second named-company migration exists: [Why We Moved off Next.js — Documenso](https://documenso.com/blog/why-we-moved-off-next-js) (not fetched; cited as a lead only).
- Counter-example in the same period — a team that migrated *to* the App Router and reports success with Server Actions: [Migrating to the Next.js App Router (or: how I learned to stop worrying and love Server Actions), Money Forward engineering blog, 2025-12-04](https://global.moneyforward-dev.jp/2025/12/04/migrating-to-the-next-js-app-router-or-how-i-learned-to-stop-worrying-and-love-server-actions/) (not fetched).
- Security as a dissent argument is now evidence-backed rather than speculative: two critical CVEs in the RSC/middleware surface within nine months — CVE-2025-29927 (CVSS 9.1, middleware auth bypass, 2025-03) and CVE-2025-55182 / "React2Shell" (CVSS 10.0, pre-auth RCE in RSC Server Functions, 2025-12). See §5 for full source list.

### Where sources disagree (explicit, for the report-writer)
1. **Is the boundary a simplification or a split?** Vercel: RSC means "a separate data-loading step does not need to pass initial props to the component tree" ([Server and Client Boundary](https://nextjs.org/docs/app/guides/server-and-client-boundary)). Caruso: it forces interactive UI to be split across files and graphs because server-rendered output "can not be modified after mounting" ([paperclover.net](https://paperclover.net/blog/webdev/one-year-next-app-router)).
2. **Navigation cost.** Vercel: "`next/link` … automatically prefetches routes, giving you the fast page transitions of a strict SPA" ([SPA guide](https://nextjs.org/docs/app/guides/single-page-applications)). Caruso: every navigation must hit the server regardless of client-held data ([paperclover.net](https://paperclover.net/blog/webdev/one-year-next-app-router)). These are reconcilable (prefetch hides latency; the request still happens) but the *architectural* claim — the client cannot serve a navigation from data it already has — stands unrebutted in what I fetched.
3. **Is Next.js's backend layer sufficient?** Next.js docs themselves concede the limit: "Next.js backend capabilities are **not a full backend replacement**" ([Backend for Frontend](https://nextjs.org/docs/app/guides/backend-for-frontend)), plus lambda constraints (no cross-request state, no WebSockets, timeouts). This is Vercel agreeing with a common critique, and is the strongest official support for keeping a separate backend API.
4. **Middleware for auth.** Historically a widespread community pattern; current docs now say Proxy "should not be your only line of defense" and CVE-2025-29927 showed the failure mode was exploitable with one header ([Authentication](https://nextjs.org/docs/app/guides/authentication); [Snyk](https://snyk.io/blog/cve-2025-29927-authorization-bypass-in-next-js-middleware/)). Any pre-2025 source recommending middleware-based authorization should be marked **superseded**.

### Gaps / claims I could NOT verify — do not report these as fact
- **"State of JS 2025: Next.js satisfaction dropped from 68% to 55%, the largest decline of any framework."** This surfaced only in a low-authority aggregator blog, not in the State of JS survey itself. **Unverified — omit or explicitly hedge.**
- **"Lee Robinson said the App Router is 'easy but not simple'."** Also surfaced only via an aggregator paraphrase; I found no primary Lee Robinson post or talk saying this. **Unverified attribution — do not quote.**
- **"Six RSC-related CVEs in two months."** Aggregator claim; I verified two CVEs (29927, 55182) from credible vendors and nothing about a count of six. **Unverified.**
- I did not fetch a Vercel or Next.js response to the paperclover critique, so the rebuttal side of dispute (1) and (2) is under-sourced.
- I found no credible, named critique specifically of the App Router **file conventions** (as opposed to RSC/caching). The critiques target the rendering and data model.
