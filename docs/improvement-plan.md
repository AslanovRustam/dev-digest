## Что уже сделано хорошо

Это не вежливость, а граница аудита: перечисленное ниже проверено и трогать не нужно.

- **Типовая гигиена отличная.** Во всём `server/src` два `any`, в `client/src` — ноль, `@ts-ignore` нет
  нигде. Контракты на Zod, типы выводятся через `z.infer`.
- **Базовая защита периметра на месте:** `helmet`, `@fastify/cors`, `@fastify/rate-limit` (120 req/min),
  точечные лимиты на дорогих маршрутах (`POST /pulls/:id/review` — 10/min), `/health` выведен из-под лимита.
- **Сырого SQL почти нет** — три `db.execute` на служебные операции, всё остальное через Drizzle.
- **Параметры маршрутов валидируются** общими схемами из `modules/_shared/schemas.ts`.
- **Тесты есть и разложены по уровням:** 18 unit + 6 интеграционных на сервере, 4 в reviewer-core,
  18 в client, 8 e2e-flow. CI разделён по пакетам и отсекает `*.it.test.ts` из unit-прогона.
- **Хуки клиента чистые.** `lib/hooks/reviews.ts` — это проводка React Query и один SSE-эффект,
  бизнес-правил внутри нет. Ровно та модель, которую предписывает `frontend-ui-architecture`.

## P1 — фундамент

### 1. ESLint отсутствует полностью

Ни одного `eslint.config.*`, ни одного `.eslintrc`, ни одного скрипта `lint` ни в одном из четырёх
`package.json`. CI гоняет только `typecheck` и `vitest`.

Почему это первым пунктом: без линтера **невозможно принудить ни одно правило размещения** из
`frontend-ui-architecture` — направление импортов, запрет боковых связей, запрет агрегирующих
barrel'ов существуют только как текст. Дополнительно не проверяются `react-hooks/exhaustive-deps`
(а в `hooks/reviews.ts` есть ручной `useEffect` с подпиской на SSE) и неиспользуемый код.

Что сделать: `eslint.config.js` в `client/` и `server/`, правило `import/no-restricted-paths` с
зонами из `.claude/skills/frontend-ui-architecture/examples.md` §7, скрипт `lint` в обоих
`package.json`, шаг в обоих workflow. Начать с `warn`, чтобы не блокировать существующий код,
и поднять до `error` после разбора.

### 2. Ни одной транзакции на весь сервер

`grep '\.transaction('` по `server/src` не находит ничего, при этом многотабличные записи есть:

```
server/src/modules/reviews/repository/review.repo.ts:25   insert(t.reviews)   ← отдельный statement
server/src/modules/reviews/repository/review.repo.ts:36   insert(t.findings)  ← отдельный statement
```

Падение между этими двумя вставками оставляет ревью без находок — запись, которая выглядит
завершённой, но пуста. Та же форма в `run.repo.ts` (`agentRuns` → `runTraces`) и в
`pull.repo.ts` (`prIntent`).

Что сделать: обернуть связанные вставки в `db.transaction(async (tx) => …)`. Начать с
`review.repo.ts` — это единственная находка аудита с риском потери данных.

Отдельно: в `server/INSIGHTS.md` уже есть запись «findings disappeared», но она про другое — про
недетерминизм модели на повторном прогоне. Частичная запись дала бы тот же симптом при другой
причине, так что после транзакций диагностическая развилка из той записи станет надёжнее.

## P2 — корректность и устойчивость

### 3. Нет ни одного error boundary

Ни `ErrorBoundary`, ни `componentDidCatch` в `client/src`, ни одного `error.tsx` в `src/app/`.
Исключение в любом компоненте разрушает всё дерево маршрута, и пользователь получает дефолтный
экран ошибки Next без возможности повторить действие на месте. `react-best-practices` оценивает
error boundaries как HIGH.

Важно: это **не** противоречит решению не использовать `loading.tsx` — состояния загрузки здесь
осознанно живут в TanStack Query. Ошибки рендера — другой класс, их Query не ловит.

Что сделать: `error.tsx` на уровне `app/` и на уровне тяжёлых маршрутов
(`repos/[repoId]/pulls/[number]/`), с кнопкой `reset()`.

### 4. Тела запросов валидируются непоследовательно

`agents/routes.ts` — эталон: 23 Zod-конструкции, тела разобраны схемами. Остальные модули
валидируют только params. В `reviews/routes.ts` это записано прямым текстом:

```
// Body stays a tolerant manual parse (both fields optional; empty body is OK).
```

«Толерантный ручной разбор» означает, что контракт держится на соглашении, а не на схеме, и
расхождение с `vendor/shared` обнаружится в рантайме.

Что сделать: поднять тела POST/PATCH до Zod-схем по образцу `agents`, переиспользуя контракты из
`vendor/shared`. Начать с `reviews` и `pulls` — там тела реально есть.

*Проверено и снято:* `workspace/routes.ts` без схемы — это один GET без пользовательского ввода,
валидировать нечего.

### 5. Индексы на активных таблицах

| Файл схемы | Таблиц | Индексов |
|---|---|---|
| `db/schema/agents.ts` | 3 | **0** |
| `db/schema/core.ts` | 4 | 1 |
| `db/schema/pulls.ts` | 3 | 2 |

Postgres **не** создаёт индекс на колонку внешнего ключа автоматически — только на ту, на которую
ссылаются. Выборки вида «все версии агента», «все прогоны PR» идут seq scan'ом.

Что сделать: индексы на FK-колонки активных таблиц плюс на пары, по которым реально фильтруют
(`findings(reviewId)`, `agentRuns(pullId, createdAt)`). Генерировать через `pnpm db:generate` —
миграции руками не править.

*Не трогать:* таблицы будущих уроков. `AGENTS.md` прямо говорит, что пустые таблицы — это замысел,
а не мёртвый код; индексы им пока не нужны.

## P3 — архитектурная гигиена, дёшево

### 6. Единственное нарушение barrel-правила

`client/src/lib/hooks/index.ts` — `export *` над пятью модулями: ровно тот агрегирующий barrel,
который `frontend-ui-architecture` запрещает вне дизайн-системы. Остальные 56 `index.ts` в проекте —
корректные однострочные фасады.

Что сделать: импортировать из доменного файла напрямую (`@/lib/hooks/reviews`). Комментарий в самом
файле уже признаёт, что оба пути работают, — значит, переход безболезненный.

### 7. Четыре `helpers.ts` на сервере — на самом деле мапперы

`modules/{agents,repos,reviews,settings}/helpers.ts` содержат `toAgentDto`, `toRepoDto`,
`findingRowToDto`, `rowsToSettings` — у них одна ясная задача, и она не «helpers».

Что сделать: переименовать в `dto.ts`. Формально `frontend-ui-architecture` покрывает фронтенд, но
аргумент против категорийных имён (Fowler, Cheney) от языка не зависит, а здесь честное имя уже
известно.

### 8. Непокрытые чистые функции и модули

- `client/src/lib/`: тесты есть у `findings.ts` и `format.ts`; нет у `github-urls.ts`,
  `model-label.ts`, `feature-models.ts` — при том что это чистые функции, которые тестируются
  вызовом, без рендера.
- Серверные модули без единого теста: `repos`, `polling`, `workspace`.

### 9. Крупные модули — кандидаты на разбор

`repo-intel/service.ts` (764), `adapters/astgrep/index.ts` (639), `repo-intel/repository.ts` (618),
`reviews/run-executor.ts` (439).

Размер сам по себе не дефект — ни один авторитетный источник не задаёт порога, и скил это фиксирует.
Смотреть надо на причины изменения: если `repo-intel/service.ts` меняется и при смене стратегии
индексации, и при смене формата выдачи — это два модуля в одном файле.

### 10. `components/mermaid-diagram` без потребителей

Ни один компонент его не импортирует; единственное другое упоминание mermaid — в контракте
`vendor/shared/contracts/knowledge.ts`.

**Сначала проверить, потом трогать.** `AGENTS.md` предупреждает, что ссылки на будущие уроки — не
пропавшие файлы. Вероятно, компонент запаркован под урок про knowledge-граф. Если так — оставить и
добавить строку в `client/AGENTS.md`, чтобы следующий аудит не спотыкался.

## Что осознанно НЕ вынесено в находки

- **Каждая страница — `"use client"`, `useParams()` вместо prop `params`, нет route handlers и
  server actions.** Это согласованная позиция, задокументированная в `client/AGENTS.md`, и
  соответствие правилу Next.js «выбери одну архитектуру данных и не смешивай». Не дефект.
- **Отсутствие `loading.tsx`** — состояния загрузки живут в TanStack Query.
- **Пустые таблицы уроков** — по замыслу.
- **Типизация** — править нечего.
