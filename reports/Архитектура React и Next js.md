# Синтезируем архитектурный канон React и Next.js

Главный вывод: **у React нет официальной позиции по структуре проекта вообще** — единственное официальное высказывание команды React живёт в архиве (`legacy.reactjs.org`), а react.dev не имеет страницы-преемника ([React legacy docs](https://legacy.reactjs.org/docs/faq-structure.html)). Next.js же прямо называет себя «**unopinionated** about how you organize and colocate your project files» ([Next.js docs](https://nextjs.org/docs/app/getting-started/project-structure)). Это значит, что любой skill по архитектуре фронтенда неизбежно кодирует не «стандарт», а **выбранную позицию** в нескольких открытых спорах — и его ценность прямо зависит от того, насколько честно он это признаёт. При этом консенсус существует там, где его обычно не ищут: colocation (единственный принцип без единого источника-диссидента), направленность импортов (shared → features → app), именование модулей по назначению, а не по категории, и жёсткое правило react.dev «нет вызовов хуков — нет префикса `use`». А самая большая опасность для skill — это фольклор, который звучит как канон: различение `utils`/`helpers`, «правило трёх», лимиты строк в компоненте, термины «god component» и «god hook». Ни одно из этого не имеет авторитетного источника, зато у **противоположных** утверждений источники есть — Fowler, Cheney и FSD прямо ругают категорийные имена папок, а react.dev открытым текстом **допускает** prop drilling на дюжину уровней. Отдельно: документация Next.js на момент исследования (2026-09-29) отдаёт версию **16.3.7**, и `middleware.ts` в ней **переименован в `proxy.ts`** — это обесценивает значительную часть текстов 2023–2025 годов про auth в middleware.

# ЧАСТЬ ПЕРВАЯ. СИНТЕЗИРОВАННЫЕ АРХИТЕКТУРНЫЕ РЕКОМЕНДАЦИИ

## Версия, на которую нацелены рекомендации: docs Next.js 16.3.x, рантайм проекта Next.js 15.1

Пять заметок расходятся в системе отсчёта, и это надо развести явно. Один исследователь зафиксировал, что `nextjs.org/docs` на 2026-09-29 обслуживает **версию 16.3.7**, а страницы несут `lastUpdated` от 2026-06 до 2026-09 ([Project structure](https://nextjs.org/docs/app/getting-started/project-structure), `lastUpdated 2026-07-21`; [Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components), `2026-08-25`; [Fetching Data](https://nextjs.org/docs/app/getting-started/fetching-data), `2026-09-07`). Другой строил рассуждения вокруг Next.js 15 и релизного блога 2024-10-21 ([Next.js 15](https://nextjs.org/blog/next-15)). Примирение такое: **нормативный источник — текущая документация 16.3.x**, потому что именно она описывает актуальные правила границ, файловых конвенций и слоя данных; релизный блог Next 15 остаётся первоисточником по двум архитектурным breaking changes, которые **до сих пор в силе** — перевод request-scoped API (`cookies`, `headers`, `draftMode`, `params`, `searchParams`) в промисы и разворот кэширования по умолчанию с «кэшируем» на «не кэшируем» для `GET` Route Handlers и Client Router Cache ([Next.js 15](https://nextjs.org/blog/next-15)). Поверх этого в 2026 году лежит opt-in модель **Cache Components** (`cacheComponents`, `cacheLife`, `updateTag`), и именно она создаёт единственную конкретную будущую ловушку для проекта-заказчика (см. последний раздел).

Самое важное для skill — **переименование `middleware.ts` → `proxy.ts`**. В текущей таблице top-level файлов `middleware.ts` отсутствует, а появился `proxy.ts` («Next.js request proxy»); руководства по authentication и BFF пишут `proxy.ts` и `export default async function proxy(req)`, отмечая, что «third-party libraries may still refer to `proxy` as `middleware`» ([Project structure](https://nextjs.org/docs/app/getting-started/project-structure); [Authentication](https://nextjs.org/docs/app/guides/authentication)). Исследователь **не** нашёл changelog-страницы, фиксирующей сам факт и версию переименования, — так что провенанс помечен как «высокая уверенность, не подтверждено первоисточником». Практический вывод для skill двойной: во-первых, любой текст, обучающий авторизации в middleware, надо считать **superseded**; во-вторых, само переименование — сигнал смены смысла: файл теперь называется прокси, а не шлюзом безопасности, и документация прямо говорит, что Proxy «should not be your only line of defense» ([Authentication](https://nextjs.org/docs/app/guides/authentication)).

## Где живут компоненты: feature-first победил на верхнем уровне, спор идёт о количестве церемонии

Ось разногласий — **не** «features против types». На верхнем уровне feature-first приняли практически все. Ось — **сколько формализма и принуждения вы покупаете**. React и Next.js продают ноль: «If you're just starting a project, don't spend more than five minutes on choosing a file structure», плюс потолок вложенности «a maximum of three or four nested folders within a single project» ([React legacy docs](https://legacy.reactjs.org/docs/faq-structure.html)). Robin Wieruch продаёт постепенный рост: один файл → много файлов → папка на компонент → технические папки, причём домены он вводит, когда в папке набирается примерно **10–15** компонентов, и настаивает на **обоих** слоях одновременно — технические папки для project-agnostic кода плюс доменные для бизнес-логики ([Robin Wieruch](https://www.robinwieruch.de/react-folder-structure/)). Bulletproof React продаёт три жёстких правила и ESLint-зоны: никаких barrel-файлов, никаких cross-feature импортов, односторонний поток shared → features → app ([bulletproof-react](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)). Feature-Sliced Design продаёт полную алгебру слоёв — App → Pages → Widgets → Features → Entities → Shared, срезы (slices) как бизнес-домены и сегменты (`ui`, `api`, `model`, `lib`, `config`) как техническое назначение, с правилом «A module (file) in a slice can only import other slices when they are located on layers strictly below» ([FSD Overview](https://feature-sliced.design/docs/get-started/overview); [FSD Layers](https://feature-sliced.design/docs/reference/layers)).

Подходы **вложены, а не альтернативны**. Bulletproof React ≈ feature-first + type-based *внутри* фичи + однонаправленные слои. FSD ≈ Bulletproof с большим числом слоёв, формальной изоляцией срезов и escape hatch `@x`. Screaming Architecture — это **мотивация** для feature-first, а не конкурирующая раскладка: тест Мартина «do they scream: **Health Care System**, or **Accounting System**?» ([Robert C. Martin, 2011](https://blog.cleancoder.com/uncle-bob/2011/09/30/Screaming-Architecture.html)). Atomic Design в этом ряду — чужой: это таксономия **дизайн-системы**, которую систематически выдают за файловую структуру, причём сам Frost пишет, что «atomic design is not a linear process» и «atomic design is not rigid dogma», и одобрительно приводит GE Design, переименовавшую всю таксономию ([Brad Frost, Ch.2, 2016](https://atomicdesign.bradfrost.com/chapter-2/)). Книга 2016 года ничего не знает про хуки, RSC и границы server/client — как словарь дизайн-системы она авторитетна, как архитектура приложения устарела.

Практические выводы, которые skill может брать без риска. Папка-на-компонент оправдана в момент, когда у компонента появляются спутники — тесты, стили, под-компоненты, типы, хелперы; до этого один файл корректен ([Robin Wieruch](https://www.robinwieruch.de/react-folder-structure/); [Josh Comeau](https://www.joshwcomeau.com/react/file-structure/)). Абсолютные импорты через path alias (`@/*`) снимают ровно ту боль относительных путей, из-за которой React вводил потолок вложенности ([bulletproof-react, project-standards](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-standards.md); [Kettmann/Profy.dev](https://dev.to/profydev/screaming-architecture-evolution-of-a-react-folder-structure-4g25)). Kebab-case для файлов и папок, принудительно через `eslint-plugin-check-file`, — самый распространённый выбор 2025–2026 и заодно защита от регистро-нечувствительных файловых систем Windows/macOS ([bulletproof-react](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-standards.md); [Kettmann/Profy.dev](https://dev.to/profydev/screaming-architecture-evolution-of-a-react-folder-structure-4g25)). И главное: **правило линтера и есть правило продвижения кода**. Под зонами Bulletproof React разделить код между двумя фичами буквально невозможно иначе, чем подняв его в shared — так что «rule of two» там не стилевое предпочтение, а механическое следствие направленности импортов ([bulletproof-react](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)).

Colocation — единственный принцип во всей теме **без единого несогласного источника**. Формулировка Kent C. Dodds: «Place code as close to where it's relevant as possible», альтернативная — «Things that change together should be located as close as reasonable»; аргумент анти-деградационный, по аналогии с комментариями к коду: разнесённые артефакты расходятся, а colocation делает удаление и изменение **видимо полными**. Пределов ровно два: E2E-тесты живут в корне, потому что им всё равно, как организован `src/`, и системная документация об интеграции нескольких модулей — в README уровня папки ([Kent C. Dodds, 2019-06-17](https://kentcdodds.com/blog/colocation)). Начиная с App Router colocation перестал быть конвенцией и стал **гарантией фреймворка**: маршрут «is **not** publicly accessible until a `page.js` or `route.js` file is added», и даже после этого на клиент уходит «only the **content returned** by `page.js` or `route.js`», поэтому файлы проекта «can be **safely colocated** inside route segments» ([Next.js docs](https://nextjs.org/docs/app/getting-started/project-structure)). Приватные папки `_folder` при этом — **не обязательны**: документация прямо говорит, что «private folders are not required for colocation», и перечисляет их реальные выгоды — отделение UI от routing-логики, единообразие в экосистеме, сортировка в редакторе и «avoiding potential naming conflicts with future Next.js file conventions». Последний пункт — единственный по-настоящему технический аргумент за `_components` внутри `app/`: подчёркивание гарантирует, что будущая файловая конвенция Next.js не столкнётся с вашим файлом.

Единственное напряжение внутри «консенсуса про colocation» создаёт FSD: её сегменты (`ui`, `api`, `model`, `lib`) заново вводят группировку по типу **внутри** среза, так что компонент и его API-вызов колокированы в одном срезе, но намеренно не в одной папке ([FSD Overview](https://feature-sliced.design/docs/get-started/overview)). «Колокируй максимально» и «следуй сегментам FSD» — не одна и та же инструкция.

## Когда дробить компонент: единственный официальный критерий — форма модели данных

react.dev даёт один нормативный критерий и один намного более полезный эвристический. Нормативный — separation of concerns: «a component should ideally only be concerned with one thing. If it ends up growing, it should be decomposed into smaller subcomponents» ([Thinking in React](https://react.dev/learn/thinking-in-react)). Полезный — форма данных: «If your JSON is well-structured, you'll often find that it naturally maps to the component structure of your UI… **Separate your UI into components, where each component matches one piece of your data model**» ([Thinking in React](https://react.dev/learn/thinking-in-react)). Второй критерий лучше первого тем, что он **проверяем** и устойчив: информационная архитектура данных меняется реже, чем раскладка экрана, поэтому границы, проведённые по данным, выживают редизайн.

Дополнительные документированные триггеры извлечения: видимое дублирование разметки («Extract a `Profile` component out of it to reduce the duplication» — [Passing Props](https://react.dev/learn/passing-props-to-a-component)); **слой-транзит**, то есть «if you pass some data through many layers of intermediate components that don't use that data… this often means that you forgot to extract some components along the way», с каноническим плохим примером `<Layout posts={posts} />` вместо `<Layout><Posts posts={posts} /></Layout>` ([Passing Data Deeply with Context](https://react.dev/learn/passing-data-deeply-with-context)); и написание Effect как сигнал, что пора завернуть логику в кастомный хук ([Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)). Решение «компонент или хук» отсекается одной фразой: «Custom Hooks let you share *stateful logic* but not *state itself*. Each call to a Hook is completely independent from every other call to the same Hook» — хук годится, когда логика переиспользуется между **визуально разными** компонентами ([Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)).

Контр-давление на дробление — литература против поспешных абстракций, и она сильнее, чем принято думать. Sandi Metz: «**duplication is far cheaper than the wrong abstraction**», с восьмишаговым описанием деградации и ловушкой утопленных затрат — «the more complicated and incomprehensible the code… the more we feel pressure to retain it»; её лекарство уникально тем, что это **обратная операция**: заинлайнить абстракцию во все вызовы, в каждом оставить только выполняемую ветку, удалить остальное — «When the abstraction is wrong, the fastest way forward is back» ([Sandi Metz, 2016-01-20](https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction)). Dan Abramov приводит React-смежный случай: дедупликация математики ресайза фигур вдвое сократила код, а потом потребовались «special cases and behaviors for different handles on different shapes» — и в «грязной» версии такие правки были бы «easy as cake»; вывод — «Clean code is not a goal… **Let clean code guide you. Then let it go.**» ([Goodbye, Clean Code](https://overreacted.io/goodbye-clean-code/)). Kent C. Dodds превращает это в правило тайминга: AHA = «Avoid Hasty Abstractions», «I'm fine with code duplication until you feel pretty confident that you know the use cases for that duplicate code», и «**Optimize for change first**» ([AHA Programming](https://kentcdodds.com/blog/aha-programming)).

Разрешается это противоречие не по принципу, а по **типу дробления**, и это самый полезный синтез для skill: **дробление ради понимания дёшево и обратимо, дробление ради переиспользования дорого и липко**. Вынести `<ProductRow>` из `<ProductTable>` в том же файле не меняет ни одного контракта. Вынести общий `<DataTable>` для трёх фич — создать контракт, с которым каждое будущее требование обязано договариваться. Именно второй ход AHA-литература велит откладывать. Официальная документация, кстати, подписывается под этим для хуков напрямую: «You don't need to extract a custom Hook for every little duplicated bit of code. **Some duplication is fine.**» ([Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)).

## Props API: композиция вместо конфигурации, и удивительно терпимое отношение к prop drilling

Официальная рамка: props — это единственный аргумент компонента и граница его независимости («you can change the `person` or the `size` props inside `Profile` without having to think about how `Avatar` uses them» — [Passing Props](https://react.dev/learn/passing-props-to-a-component)). Единственный опубликованный **правилообразный** style guide по props-API, найденный во всём исследовании, — у Material UI: **boolean при 2 значениях, enum при более чем 2 или при вероятном росте**; boolean по умолчанию `false`, чтобы сокращение `<X flag />` читалось верно; имена — прилагательные и существительные, не глаголы, потому что «props describe *states* and not *actions*» (`disabled`, не `enable`); контролируемые компоненты — `value` + `onChange`, обработчики «существительное, потом глагол» (`onPageChange`) ([MUI API design approach](https://mui.com/material-ui/guides/api/)). Это ровно та ссылка, которой обычно не хватает совету «замени `isPrimary`/`isDanger`/`isGhost` на `variant`»: три взаимоисключающих boolean кодируют 8 состояний при 3 легальных.

Почему композиция бьёт конфигурацию, лучше всех сформулировал Dodds: его пример `filter()` разрастается до `filterNull`, `filterUndefined`, `filterZero`, `filterEmptyString` — **16 комбинаций флагов на 6 реальных сценариев**, с расходами в коде, документации, поддержке, ветвлении реализации и в объёме API, который пользователь не удержит в голове; лекарство — inversion of control: «**Make your abstraction do less stuff, and make your users do that instead**», с двумя React-носителями — compound components и state reducer ([Inversion of Control](https://kentcdodds.com/blog/inversion-of-control)). Compound components определены там же: «two or more components that work together to accomplish a useful task», канонический образец — `<select>`/`<option>`, а плоская альтернатива `<select options="key1:value1;key2:value2">` названа «yuck» именно потому, что делает невыразимыми атрибуты отдельного ребёнка (`disabled` на одном option); состояние родитель делит **неявно**, через Context ([Compound Components](https://kentcdodds.com/blog/compound-components-with-react-hooks)).

Про `children` официальная позиция однозначна: «You can think of a component with a `children` prop as having a 'hole' that can be 'filled in' by its parent components with arbitrary JSX. You will often use the `children` prop for visual wrappers: panels, grids, etc.» ([Passing Props](https://react.dev/learn/passing-props-to-a-component)), и MUI подтверждает ту же иерархию выбора: «Using the `children` prop is the idiomatic way to do composition with React», но при ограниченных потребностях явные props (`icon`, `label`) дают более простую реализацию ([MUI](https://mui.com/material-ui/guides/api/)). Практическая лестница выбора паттерна: произвольный контент → слот `children`; контент в нескольких именованных позициях → JSX-типизированные props или compound-пространство имён; управление порядком **и** чтение состояния родителя → compound + Context; подмена отрендеренного элемента с сохранением поведения → `asChild` (Radix) или `render` (Base UI); изменение **поведения**, а не разметки → state reducer / control props; поведение без разметочных мнений → headless-хуки в стиле React Aria.

Самый контринтуитивный официальный факт — **терпимость react.dev к prop drilling**: «**Start by passing props.** If your components are not trivial, it's not unusual to pass a dozen props down through a dozen components. It may feel like a slog, but it makes it very clear which components use which data! The person maintaining your code will be glad you've made the data flow explicit with props.» ([Passing Data Deeply with Context](https://react.dev/learn/passing-data-deeply-with-context)). Из двух официальных положений выводится рабочее правило: **метрика — не глубина, а использование**. Прокинуть prop через десять компонентов, которые его используют, — явно и нормально; через два, которые не используют, — признак пропущенной границы `children`. Context оправдывается **числом потребителей**, а не расстоянием.

## Константы, utils, helpers, типы: именуй по назначению, а не по категории

Единственная точка, где официальная документация, корпоративные style guide и эксперты сходятся полностью, — **имя модуля должно предсказывать его содержимое**. FSD формулирует нормативно: «Make sure that the name of these segments describes the purpose of the content, not its essence. For example, `components`, `hooks`, and `types` are bad segment names because they aren't that helpful when you're looking for code» ([FSD Slices and segments](https://feature-sliced.design/docs/reference/slices-segments)). Dave Cheney — тот же аргумент для пакетов: имена вида `utils`, `helpers`, `base`, `common` «describe what a package *contains* rather than what it *provides*», с двумя названными источниками появления (разрыв циклов импорта → «junk drawers»; вынос ложной общности) и лекарствами — перенести функцию в вызывающий пакет, приняв дублирование («duplication is far cheaper than the wrong abstraction» — цитата Metz у Cheney), либо создать несколько сфокусированных пакетов с описательными именами по образцу `net/http` ([Dave Cheney, 2019-01-08](https://dave.cheney.net/2019/01/08/avoid-package-names-like-base-util-or-common)). Airbnb выводит то же механически: «A base filename should exactly match the name of its default export» ([Airbnb JS Style Guide](https://javascript.airbnb.tech/)). А react.dev применяет ровно этот принцип к хукам: хорошие кастомные хуки «named after their purpose» (`useChatRoom`, `useImpressionLog`, `useOnlineStatus`), а `useMount`/`useEffectOnce`/`useUpdateEffect` заклеймены как обёртки над API вместо сценария ([Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)).

Отсюда прямо следует позиция по константам: **ни один авторитетный источник не одобряет глобальный `constants.ts`**. Предписание — колокировать по умолчанию, поднимать до **минимально достаточной** общей области при втором потребителе и называть модуль по домену (`routes`, `queryKeys`, `config`), а не по категории. У FSD это `shared/config` (env-переменные, глобальные feature flags, app-wide конфиг), `shared/routes` (константы и паттерны маршрутов) и `<slice>/config` ([FSD Layers](https://feature-sliced.design/docs/reference/layers)). Лучшая конкретная демонстрация — TkDodo про query keys: «I don't believe that storing all your Query Keys globally in `/src/utils/queryKeys.ts` will make things better», вместо этого по одной **key factory на фичу** рядом с запросами (`/src/features/Todos/queries.ts`), от самого общего к самому специфичному, со ссылкой на colocation Dodds как обоснование ([Effective React Query Keys](https://tkdodo.eu/blog/effective-react-query-keys)). Против магических литералов работает каталог Fowler — «Replace Magic Literal», `9.81` → `STANDARD_GRAVITY` ([refactoring.com](https://refactoring.com/catalog/replaceMagicLiteral.html)), а `CONSTANT_CASE` по Google допустим только для module-level символов и читается как **сигнал намерения**, «indicates that a value is *intended* to not be changed» ([Google TS Style Guide](https://google.github.io/styleguide/tsguide.html)); Airbnb строже — только для экспортируемых `const`, которым «the programmer can trust… never to change», причём вложенные свойства остаются lowercase ([Airbnb](https://javascript.airbnb.tech/)). Следствие, полезное как эвристика ревью: **файл, целиком состоящий из `CONSTANT_CASE`, сам по себе признак, что это категорийная корзина, а не модуль**.

По `enum` современная позиция официальная: «In modern TypeScript, you may not need an enum when an object with `as const` could suffice», с обоснованием «it keeps your codebase aligned with the state of JavaScript» и документированной идиомой извлечения `type Direction = typeof ODirection[keyof typeof ODirection]` ([TS Handbook: Enums](https://www.typescriptlang.org/docs/handbook/enums.html)). Google оставляет обычный `enum` легальным, но **запрещает** `const enum` ([Google TS Style Guide](https://google.github.io/styleguide/tsguide.html)); Stefan Baumgartner перечисляет три конкретных провала enum — рантайм-эмиссия, дыра в типобезопасности числовых enum («a function that takes a direction also takes any number value») и номинальная типизация строковых enum, противоречащая структурной системе TypeScript ([fettblog.eu, 2020-11-19](https://fettblog.eu/tidy-typescript-avoid-enums/)). Ни один источник enum не **требует**, поэтому дефолт для 2026 — `as const` объект плюс производный union.

Типы: доминирующее предписание — трёхуровневое правило Matt Pocock. Тип, используемый в одном месте, живёт в том же файле (и лучше инлайном в подписи, потому что отдельный `*.types.ts` усложняет одновременную правку компонента и его типов); тип для двух и более мест переезжает в общий файл **минимально достаточной области**; тип, нужный более чем одному пакету монорепо, — в общий пакет ([Total TypeScript](https://www.totaltypescript.com/where-to-put-your-types-in-application-code)). Схемная деривация закрывает вопрос структурно: «Zod infers a static type from your schema definitions. You can extract this type with the `z.infer<>` utility», плюс `z.input<>`/`z.output<>` для схем с трансформациями ([Zod basics](https://zod.dev/basics)). Общий артефакт — **модуль схемы**, а не «тип», и обе стороны выводят типы из него, так что параллельному рукописному типу просто нечему расходиться. Поскольку Zod — рантайм-значение, модуль схемы не может быть type-only модулем и принадлежит purpose-named месту (FSD `api`/`model` или пакет контрактов), а не `types/`.

Конфиг обе методологии дают отдельный purpose-named дом: `src/config` у Bulletproof React («Global configurations and environment variables») и `shared/config` у FSD. Конвенция 2025–2026 — **один граничный модуль**, который валидирует `process.env` против Zod-схемы при старте и экспортирует типизированный объект, с жёстким разделением client/server: t3-env существует ровно потому, что «Forgetting environment variables during build can be a hassle and difficult to debug», и гарантирует, что «Your server variables will be `undefined` on the client, and attempting to access one will throw a descriptive error message» ([t3-env](https://env.t3.gg/docs/introduction)). Валидированный env — лучший контрпример привычке «папка констант»: это **граничный** модуль, который парсит недоверенный ввод и падает быстро, а не мешок значений.

## Бизнес-логика: два яруса вместо слоя, и почему хук не может быть домен-слоем

Официальный ответ react.dev однозначен и даёт **двухъярусную** логику. Первый ярус — чистые функции: «If your function doesn't call any Hooks, avoid the `use` prefix. Instead, write it as a regular function *without* the `use` prefix», с примером `useSorted(items)` 🔴 → `getSorted(items)` ✅ и с прямо названной выгодой — обычную функцию можно вызвать условно, хук нельзя ([Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)). Второй ярус — кастомные хуки для всего, что касается React-состояния, подписок и внешних систем, и именование здесь несущее, а не косметическое: «This convention guarantees that you can always look at a component and know where its state, Effects, and other React features might "hide"». Прочитанное архитектурно, правило «избегай префикса `use`» — это инструкция **держать бизнес-правила вне хуков, а в хуках оставлять только обвязку**.

У хуков как «слоя логики» есть два документированных ограничения, и оба структурные. Первое: «Custom Hooks let you share *stateful logic* but not *state itself*» — два компонента, вызвавшие `useCart()`, получат две независимые корзины, и если состояние должно быть общим, документация велит «lift it up and pass it down instead» ([Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)). Это **сильнейший аргумент против** попытки сделать хуки домен-слоем приложения: всё, что обязано быть единственным в приложении, требует store, context или кэша запросов. Второе: Rules of Hooks — хуки вызываются только на верхнем уровне компонента или другого хука, и прямо запрещены в условиях, циклах, обработчиках событий, классах, функциях внутри `useMemo`/`useReducer`/`useEffect` и внутри `try`/`catch`/`finally`; «**Don't call Hooks from regular JavaScript functions.**» ([Rules of Hooks](https://react.dev/reference/rules/rules-of-hooks)). Это точная, цитируемая форма возражения «логику в хуке не переиспользовать вне React»: её не вызовет ни CLI, ни worker, ни серверный route, ни обработчик события. Плюс цена тестируемости: кастомный хук — не чистая функция, его нельзя просто вызвать в тесте (получите `Invalid hook call`), нужен `renderHook()` или компонент-носитель, то есть тестовая инфраструктура, которой обычный модуль не требует ([Kent C. Dodds](https://kentcdodds.com/blog/how-to-test-custom-react-hooks)).

Сервисный слой в React-литературе проиграл по названию: доминирует **feature-scoped API-модуль**, а не глобальный `services/`. Bulletproof React кладёт `api/` («API requests and hooks») внутрь каждой фичи, явно разрешая и централизованный вариант — «In some cases it might be more practical to keep all API calls outside of the features folders in a dedicated `api` folder» ([bulletproof-react](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)). Wieruch приходит к тому же другим путём: верхнеуровневый `api/` для централизованного клиента, **никакого** `services/`, инвариант «code flows in one direction — from shared utilities into features, and from features into pages. Never the other way around», и требование, чтобы фичи были «independent and deletable without breaking the system» ([Robin Wieruch](https://www.robinwieruch.de/react-folder-structure/)). TkDodo колокирует данные по фиче и экспортирует **только хуки**, оставляя query keys и query functions локальными ([Effective React Query Keys](https://tkdodo.eu/blog/effective-react-query-keys)). То, что Fowler называл Service Layer, на практике разошлось на **API-модуль** (транспорт + валидация) и **query-хук** (кэш, оркестрация). Обоснование самой границы у адвокатов простое: компонент «shouldn't be aware if we're using `fetch`, `axios`, or another HTTP client», ни того, «if that data is fetched via HTTP, gRPC… or any other kind of source» ([Alex Kondov, 2024-02-09](https://alexkondov.com/full-stack-tao-clean-architecture-react/)).

Разделение состояний в 2026 стандартизировано на уровне официальной документации: **server state = кэшированный снимок данных, которыми вы не владеете**, client state = данные, которыми владеет приложение. TanStack Query — «a server-state library, responsible for managing asynchronous operations between your server and client», и она «**not a replacement for local/client state management**»; после выноса асинхронного состояния по-настоящему глобальный client state у большинства приложений оказывается «very tiny», а исключением документация называет design tools ([TanStack Query docs](https://tanstack.com/query/latest/docs/framework/react/guides/does-this-replace-client-state)). Мейнтейнер переформулирует шире: «**React Query is an async state manager.** It can manage any form of asynchronous state — it is happy as long as it gets a Promise» ([TkDodo, 2021-08-20](https://tkdodo.eu/blog/react-query-as-a-state-manager)). Конвенции, которые skill может кодировать как правила: кастомный хук на каждый запрос, даже тонкий, потому что так «you can keep the actual data fetching out of the ui, but co-located with your `useQuery` call»; **query key как массив зависимостей** — «React Query will trigger a refetch whenever the query key changes», что заменяет императивную оркестрацию `refetch()`; не копировать server state в client state, потому что так вы «implicitly opt out of all background updates»; и `queryClient.setQueryData` только для оптимистичных обновлений и для данных, пришедших с бэкенда после мутации ([Practical React Query](https://tkdodo.eu/blog/practical-react-query)). Redux сам отдал эту ось: «We recommend using RTK Query as the default approach for data fetching and caching in a Redux app» ([Redux Style Guide](https://redux.js.org/style-guide/)).

Размещение состояния имеет официальную лестницу: «**Just because you need to pass some props several levels deep doesn't mean you should put that information into context**» → сначала props → потом извлечь компоненты и передать JSX как `children` → «If neither of these approaches works well for you, consider context», с предупреждением «Context is very tempting to use, but **it's too easy to overuse it**» ([Passing Data Deeply with Context](https://react.dev/learn/passing-data-deeply-with-context)). При этом react.dev **сам** называет «Managing state» (context + reducer) законным сценарием и даёт рецепт: всю обвязку держать в `TasksContext.js`, а потреблять через кастомные хуки `useTasks()`/`useTasksDispatch()`, чтобы компоненты остались «focused on what they display rather than where they get the data» ([Scaling Up with Reducer and Context](https://react.dev/learn/scaling-up-with-reducer-and-context)). Синтезированная лестница (это вывод отчёта, а не цитата одного источника): локальный `useState` → `useReducer`, когда у обновлений есть правила → подъём → композиция через `children` → context+reducer на каждую отдельную область ответственности → внешний store **только** когда состояние нужно (а) писать извне React, (б) читать вне дерева React, (в) разделять между несвязанными деревьями. Только эти три причины документированы как **архитектурные**, остальные аргументы «context — не state manager» сводятся к ре-рендерам ([Test Double](https://testdouble.com/insights/react-context-for-dependency-injection-not-state-management)).

Формы: конвенция 2025–2026 — **schema-first с общей схемой**, одна Zod-схема на клиентскую форму и на серверный action/endpoint, при этом состояние формы остаётся локальным. Самое жёсткое правило здесь официальное и принадлежит Redux: «**Avoid Putting Form State In Redux** — Most form state shouldn't go in Redux… Prefer keeping the form edits themselves in local component state» ([Redux Style Guide](https://redux.js.org/style-guide/)). Механизм React 19 — `useActionState` в паре с Server Actions, возвращающий «the current action state — including any errors your action returned», а Next.js прямо называет Zod/Valibot для валидации полей ([Next.js Forms](https://nextjs.org/docs/app/guides/forms)). Неявная во всех источниках, но нигде не сформулированная одной строкой граница доверия: **клиентская валидация — это UX, серверная — корректность**, а общая схема убирает дублирование, не сливая границу. И это же — лучший реальный пример «доменного артефакта» на фронтенде: схема framework-независима, тестируется вне React и переиспользуется на сервере, то есть служит прагматичной заменой домен-слою в 90% случаев.

Антипаттерны, документированные на авторитетном уровне, ровно четыре. Effect как производное состояние — «🔴 Avoid: redundant state and unnecessary Effect» против «✅ Good: calculated during rendering», с правилом «**transform all the data at the top level of your components**». Effect как обработчик пользовательских событий — «You don't need Effects to handle user events… By the time an Effect runs, you don't know *what* the user did». Effect как механизм загрузки данных — разрешено, но не рекомендуется, с конкретным режимом отказа (гонка: набор «hello» порождает запросы за «h», «he», «hel», «hell», «hello» без гарантий порядка ответов, лечится флагом `ignore` в cleanup) и с выводом «modern frameworks provide more efficient built-in data fetching mechanisms» ([You Might Not Need an Effect](https://react.dev/learn/you-might-not-need-an-effect)). И хуки-обёртки жизненного цикла — `useMount`, `useEffectOnce`, `useUpdateEffect` — «don't fit well into the React paradigm», причём с дополнительным аргументом, что они ослепляют линтер: «The linter won't warn you about it because the linter only checks direct `useEffect` calls» ([Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)). Сильнейшее из доступных утверждений — композитное: `useEffect` + `fetch` + `useState` в компоненте нарушает **три** документированных правила одновременно, из-за чего «you might not need an Effect» де-факто стал тестом на правильное размещение логики.

## Next.js App Router: `"use client"` — это граница графа модулей, а не пометка компонента

Самая частая ошибка понимания: `"use client"` помечает **точку входа клиентского поддерева в графе модулей**, а не один компонент. Документация: директива «is used to declare a **boundary** between the Server and Client module graphs (trees)», и «Once a file is marked with `"use client"`, **all of its imports and the components it directly renders are included in the client bundle**. This means you don't need to add the directive to every component that is intended for the client» ([Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)). Критическое исключение: «**It does not apply to Server Components passed as children or other props.** Those components are not imported into the Client Component's module graph. They are rendered on the server and passed to the Client Component as rendered output». Двухправильная формулировка из отдельного руководства: «**Code** crosses through imports… **Data** crosses through props, and it must be serializable, so functions like event handlers cannot cross», и «You only need `'use client'` at the entry to a client subtree, not on every file inside it» ([Server and Client Boundary](https://nextjs.org/docs/app/guides/server-and-client-boundary)).

Объяснение через владение — самое точное, что есть в документации: «The **owner** is the component whose source contains the JSX for a child… The **parent** directly contains the child in the rendered tree. Because `Cart`'s owner is a Server Component, `Cart` renders on the server. `Modal` is only the parent, so `Modal` receives `Cart`'s output to place but not its code to run» ([Server and Client Boundary](https://nextjs.org/docs/app/guides/server-and-client-boundary)). Поэтому **слот `children` — самый несущий композиционный примитив всей архитектуры App Router**: он позволяет stateful-клиентской оболочке (модалка, табы, аккордеон, провайдер) обернуть серверный контент, не втаскивая его код — и его импорты, включая DB-клиенты, — в браузерный бандл. Рекомендованный escape hatch для общих компонентов: «create a Client Component wrapper that imports it and place the directive on the wrapper… **puts the boundary closer to your application code**». Провайдеры — как можно глубже: «**You should render providers as deep as possible in the tree**», потому что React context в Server Components не поддерживается.

Три факта про границу, которые обычно упускают и которые обязаны быть в skill. Первое: Client Component исполняется в **обоих** средах — таблица документации даёт Server Component «на сервере: да / в браузере: нет», Client Component «на сервере: да / в браузере: да», и «The word "Client" indicates that a Client Component also runs in the browser, **alongside its server render**». То есть `"use client"` — **не** отказ от SSR; отказ требует `next/dynamic` с `{ ssr: false }`. Второе: compound components ломаются на границе — «A Server Component that imports a Client Component receives a client reference instead of the function. As a result, `Menu.Item` is `undefined`, and React throws "Element type is invalid."», лечится экспортом частей как **named exports** вместо статических свойств. Третье: TypeScript не различает Server Function от обычной функции, поэтому Next.js ввёл эвристику по имени — плагин разрешает prop-функцию «when its name is `action` or ends in `Action`» и флагует остальные. Это не косметика: это единственный механизм, которым система типов отличает легальный prop-серверную-функцию от нелегального обработчика событий.

Защита границы обеспечивается двумя пакетами-пока-ёкэ и одной конвенцией имён переменных. `server-only` в модуле делает ошибку **сборки** при импорте его в Client Component; `client-only` — зеркальная пометка для модулей с `window`. Установка при этом опциональна и пакеты пустые: «Next.js handles `server-only` and `client-only` imports internally… **The contents of these packages from NPM are not used by Next.js**» ([Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)). Вторая половина защиты — env: в клиентский бандл попадают только переменные с префиксом `NEXT_PUBLIC_`, остальные заменяются пустой строкой, из-за чего утёкшая `getData()` «can be imported and executed on the client, [but] it won't work as expected» — то есть отказ **молчаливый**, и именно поэтому `server-only` рекомендуется сверху. Архитектурно: `server-only` — это механизм, превращающий «слой данных живёт на сервере» из конвенции в ошибку компиляции.

## Файловые конвенции App Router — это набор границ, которые роутер устанавливает за вас

`app/` — файловый роутер, где папки задают сегменты URL, а сегмент становится публично доступным только при наличии `page` или `route`. Всё остальное — **границы**: `layout` = устойчивая оболочка, `template` = переустанавливаемая оболочка, `error`/`global-error` = React error boundaries, `loading` = Suspense boundary, `not-found` = error boundary для «не найдено», `default` = fallback для параллельного слота. Порядок композиции фиксирован и является архитектурным контрактом того, где сидят границы: `layout.js` → `template.js` → `error.js` → `loading.js` → `not-found.js` → `page.js` или вложенный `layout.js`, «rendered recursively in nested routes» ([Project structure](https://nextjs.org/docs/app/getting-started/project-structure)).

| Конвенция | Архитектурная роль | Когда нужна |
|---|---|---|
| `layout` | устойчивая оболочка, **не** перерендеривается при навигации | всегда (root), далее по вкусу |
| `template` | оболочка, которая **перемонтируется** на каждую навигацию | per-navigation эффекты, анимации входа, сбрасываемое состояние |
| `error` / `global-error` | React error boundary; `global-error` — единственная выше root layout, поэтому рендерит свои `<html>`/`<body>` | всегда, если не хотите белый экран |
| `loading` | Suspense boundary для сегмента | при серверных данных; `<Suspense>` вручную — ближе к месту доступа к данным |
| `not-found` | error boundary «не найдено» | при динамических сегментах |
| `default` | fallback слота при hard navigation | только когда есть `@slot` |
| `(group)` | организация без влияния на URL; позволяет несколько root layouts и локальный `loading.tsx` | по необходимости |
| `_folder` | вывод папки и всех вложенных из роутинга | опционально; единственный твёрдый аргумент — forward-compat с будущими конвенциями |

Разница `template` против `layout` — это решение о **времени жизни состояния**, а не о стилях; и именно непрерывность layout делает его непригодным для auth-проверок (см. ниже). `default.tsx` имеет смысл только при параллельных маршрутах. Отдельный неочевидный факт с последствиями для безопасности: параллельные слоты рендерятся «**including parallel route slots whether or not they are displayed**» ([Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)).

По организации файлов Next.js даёт три равноправные стратегии и отказывается их ранжировать: хранить файлы проекта **вне** `app` (оставив `app` чисто для роутинга), хранить их в top-level папках **внутри** `app`, либо **разделить по фиче/маршруту** (глобально общий код в корне `app`, специфичный — внутрь сегментов). Вывод документации: «The simplest takeaway is to choose a strategy that works for you and your team and be consistent across the project», плюс дисклеймер собственных примеров: «we're using `components` and `lib` folders as generalized placeholders, **their naming has no special framework significance**» ([Project structure](https://nextjs.org/docs/app/getting-started/project-structure)). Следствие для skill: любой источник, утверждающий, что Next.js **рекомендует** `app/_components` вместо `src/components`, перечитывает документацию — это просто две из трёх стратегий, и ни одна не предпочтена.

## Слой данных: три санкционированных архитектуры, и запрет ставить авторизацию в layout

Next.js теперь документирует **три** архитектуры доступа к данным и велит выбрать ровно одну: «**HTTP APIs**: for existing large applications and organizations. **Data Access Layer**: for new projects. **Component-Level Data Access**: for prototypes and learning», с явным «**We recommend choosing one data fetching approach and avoiding mixing them.** This makes it clear for both developers working in your code base and security auditors what to expect» ([Data security](https://nextjs.org/docs/app/guides/data-security)). Вариант с внешним API — **первоклассный**, а не отступление: «You should follow a **Zero Trust** model when adopting Server Components in an existing project. You can continue calling your existing API endpoints such as REST or GraphQL from Server Components using `fetch`», и он подходит, когда «You already have security practices in place. **Separate backend teams use other languages or manage APIs independently**». DAL определён так: внутренняя библиотека, которая «**Only run on the server. Perform authorization checks. Return safe, minimal Data Transfer Objects (DTOs)**», причём «**only the Data Access Layer should access `process.env`**». Component-level доступ помечен как антипаттерн прямо в коде с комментарием `// EXPOSED:`.

Где живёт авторизация — самая жёсткая часть текущей документации. Заголовочное правило: «While Proxy can be useful for initial checks, **it should not be your only line of defense in protecting your data. The majority of security checks should be performed as close as possible to your data source**» ([Authentication](https://nextjs.org/docs/app/guides/authentication)). Proxy ограничен **оптимистичными** проверками по конструкции: «since Proxy runs on every route, including prefetched routes, it's important to **only read the session from the cookie (optimistic checks), and avoid database checks**». Layout — **не** граница авторизации, по двум независимым причинам: «these **don't re-render on navigation**, meaning the user session won't be checked on every route change», и «**A layout also does not control whether the rest of the route renders.** Route segments and parallel route slots are rendered by the router, so a layout that hides or swaps them does not stop them from running or from appearing in the RSC Payload». SPA-привычка названа и отклонена: «A common pattern in SPAs is to `return null` in a layout or a top-level component if a user is not authorized. **This pattern is not recommended** since Next.js applications have multiple entry points». Это, вероятно, самое недооценённое архитектурное ограничение App Router: оно вычёркивает весь привычный React-приём «защитить поддерево в одном месте». `params` и `searchParams` — недоверенный пользовательский ввод: «**BAD: Trusting searchParams directly**» → «**GOOD: Re-verify every time**» из cookie.

Исторический контекст, который надо унести в skill: **CVE-2025-29927** (раскрытие 2025-03-21, CVSS 9.1) — обход авторизации в middleware через один заголовок `x-middleware-subrequest`, затрагивал версии до 12.3.5 / 13.5.9 / 14.2.25 / 15.2.3 ([Snyk](https://snyk.io/blog/cve-2025-29927-authorization-bypass-in-next-js-middleware/); [ProjectDiscovery](https://projectdiscovery.io/blog/nextjs-middleware-authorization-bypass)). Он не **создал** правило «не авторизуй в middleware» — оптимистично-безопасное разделение предшествовало ему, — но превратил его из замечания о производительности в требование безопасности, а переименование в `proxy.ts` закрепило смену смысла. Второй, ещё более серьёзный случай — **CVE-2025-55182** («React2Shell», декабрь 2025, CVSS 10.0), pre-auth RCE в обработке Server Functions RSC ([Akamai](https://www.akamai.com/blog/security-research/cve-2025-55182-react-nextjs-server-functions-deserialization-rce); [Datadog](https://securitylabs.datadoghq.com/articles/cve-2025-55182-react2shell-remote-code-execution-react-server-components/)).

Разделение труда между Server Actions, Route Handlers и отдельным API документация не сводит в одну таблицу, но правило извлекается однозначно. Server Actions — примитив **мутаций**: «Their primary purpose is to mutate data from your frontend client. Server Actions are queued. **Using them for data fetching introduces sequential execution**» ([Backend for Frontend](https://nextjs.org/docs/app/guides/backend-for-frontend)); и они **публичные endpoint'ы**: «even if a Server Action or utility function is not imported elsewhere in your code, it can still be called externally», причём «**A page-level authentication check does not extend to the Server Actions defined within it. Always re-verify inside the action**» ([Data security](https://nextjs.org/docs/app/guides/data-security)). Route Handlers — **публичный API-слой** для не-UI ответов, вебхуков, callback-URL, проксирования и CORS, и Next.js сам ставит себе предел: «**Next.js backend capabilities are not a full backend replacement.**» Жёсткий антипаттерн назван прямо: «**Fetch data in Server Components directly from its source, not via Route Handlers.** For Server Components prerendered at build time, using Route Handlers **will fail the build step**». Отсюда: при наличии отдельного бэкенда `app/api/*/route.ts` **избыточен для чтения** и оправдан только вебхуками/callback'ами, сокрытием креденшела, same-origin cookie/CORS и переформатированием ответа.

Про клиентскую загрузку данных документация не просто разрешает, а благословляет библиотеки: «Use a client data-fetching library such as SWR, TanStack Query, or Apollo Client when Client Components need a **shared browser cache**», с отдельной под-страницей руководства по TanStack Query и таблицей паттернов (`useQuery` / `useSuspenseQuery` / `<HydrationBoundary>`) ([Client-side data fetching](https://nextjs.org/docs/app/guides/client-side-data-fetching)). И тут же предупреждение, которое надо кодировать как правило ревью: сосуществовать могут **три** слоя кэша — серверный кэш Next.js, клиентский кэш Next.js (RSC payloads) и кэш самой библиотеки, — «**Cache identities and mutation invalidation must stay coordinated across layers.**»

Наконец, направление, в котором двинулась официальная позиция по «кто имеет право загружать данные», противоположно ортодоксии 2015–2019: «Identical `fetch` requests in a React component tree are memoized by default, so **you can fetch data in the component that needs it instead of drilling props**», а для ORM/DB — обёртка в `React.cache`, чтобы «Multiple components can then call the function within the same request while sharing one result» ([Fetching Data](https://nextjs.org/docs/app/getting-started/fetching-data)). TkDodo говорит то же про клиент: «Your component can fetch its own data, co-located, right where you need it to be», и колокированные запросы делают компоненты «more independent because you can move them around freely» ([React Query as a State Manager](https://tkdodo.eu/blog/react-query-as-a-state-manager)). Механизм, который сделал это безопасным, — **дедупликация запросов** (`fetch` memoization, `React.cache`, кэш по query key): второй вызов за теми же данными бесплатен, поэтому архитектурное давление развернулось **вниз**, к компоненту, которому данные нужны. Выжившая полезная форма старого различения: **компонент, владеющий зависимостью от данных, должен быть достаточно отделим, чтобы его можно было обернуть в `<Suspense>`** (на сервере) или чтобы он владел собственным `useQuery` с собственными loading/error (на клиенте). Это правило о том, где живут состояния загрузки, а не о том, в какой папке лежит компонент.

# ЧАСТЬ ВТОРАЯ. ОТКРЫТЫЕ СПОРЫ, НЕГАТИВНЫЕ РЕЗУЛЬТАТЫ И МАСТЕР-СПИСОК ИСТОЧНИКОВ

## Пять споров, по которым skill обязан занять позицию — и которые нельзя разрешить ссылкой на авторитет

### Спор 1. Barrel-файлы (`index.ts`): самая острая развилка всей темы

**Против** — TkDodo, Hagemeister, Bulletproof React. Четыре документированных аргумента: циклические импорты (импорт из barrel **внутри его же директории** создаёт цикл, который JS терпит, а бандлеры валят с непонятными ошибками, и auto-import редактора создаёт такие циклы молча); раздувание графа модулей (измеренный кейс TkDodo: Next.js-проект с **11k модулей (5–10 с)** после удаления внутренних barrels упал до **3.5k** — минус 68%); суперлинейный рост стоимости тулинга (замеры Hagemeister на M1: 500 модулей 0.15 с, 1 000 — 0.31 с, 10 000 — 3.12 с, 25 000 — 16.81 с, 50 000 — 48.44 с; поскольку Jest перестраивает граф на каждый тестовый файл в изолированном процессе, а линтеры работают по файлу, проект из 100 тестовых файлов платит ≈**1 м 18 с** на 10k модулей, ≈**7 мин** на 25k и ≈**20 мин** на 50k, откуда вывод «Get rid of all barrel files» и заявка на 60–80% улучшения); и хрупкость автоматического escape hatch — `optimizePackageImports` работает только на «чистых» barrel'ах, и единственный `export const foo = 5` отключает оптимизацию из-за возможных сайд-эффектов ([TkDodo, 2024-07-26](https://tkdodo.eu/blog/please-stop-using-barrel-files); [Marvin Hagemeister, 2023-10-08](https://marvinh.dev/blog/speeding-up-javascript-ecosystem-part-7/)). Правило TkDodo с единственным исключением: в прикладном коде barrel'ов не должно быть — «you're just making your life harder by putting `index.ts` files into arbitrary directories» — но для **публичного API библиотеки** они уместны и необходимы.

**За** — Josh Comeau и FSD. Comeau прямо спорит с «anti-barrel movement» применительно к приложениям: «the bundler will spend most of its time dealing with third-party dependencies. **Less than 1% of the modules that the bundler encounters will be barrel files**», и его пост обновлён **2025-12-03**, то есть **после** статьи TkDodo, значит это обдуманная позиция, а не устаревший совет ([Josh Comeau](https://www.joshwcomeau.com/react/file-structure/)). FSD же **требует** публичного API, реализованного index-файлами с реэкспортами ([FSD Public API](https://feature-sliced.design/docs/reference/public-api)).

Почему спор не решается: **стороны меряют разные метрики** — латентность сборки/тулинга против эргономики импортов и инкапсуляции, и поэтому ни одна не опровергает другую. Асимметрия качества доказательств при этом реальна: у TkDodo и Hagemeister есть замеры, у Comeau — оценка доли без бенчмарка. Существует и **задокументированный компромисс**, причём предложенный самой FSD, которая **называет статью TkDodo по имени** и признаёт, что «having a large amount of index files in a project can slow down the development server»; её меры — отдельные index-файлы **на компонент** внутри `shared/ui` и `shared/lib`, **отказ** от index-файлов в сегментах слоёв, и монорепо для крупных проектов; плюс FSD полностью **запрещает** wildcard-реэкспорты, помечая `export * from "./ui/Comment"` как «❌ BAD CODE BELOW, DON'T DO THIS», потому что это вредит discoverability и случайно экспонирует внутренности ([FSD Public API](https://feature-sliced.design/docs/reference/public-api)). Узкий синтез, который приняли бы все: barrel'ы **на границах пакета/среза, которые вы действительно хотите инкапсулировать**, никогда — в произвольных промежуточных директориях, никогда — wildcard, никогда — импорт из barrel'а внутри той же директории. Архитектурная цена решения: barrel — единственный ванильный TS-механизм публичного API модуля, поэтому команды, отказавшиеся от barrel'ов, теряют принудительную инкапсуляцию и обязаны заменить её lint-ограничениями путей. Bulletproof React делает ровно это — его правило «no barrels» и его конфиг `import/no-restricted-paths` суть одно и то же решение. Следствие: barrel-решение **определяет гранулярность** доступного принуждения границ — lint-зоны ограничивают **директорию**, из которой можно импортировать, а barrel'ы ограничивают ещё и **символы**.

### Спор 2. Bulletproof React против FSD: как лечить cross-feature связность

Запрещают оба одно и то же — связность сиблингов, — но лечат по-разному. Bulletproof React: «It might not be a good idea to import across the features. Instead, compose different features at the application level», то есть **поднять** связность вверх, к app-слою, принудительно через `import/no-restricted-paths` с зоной **на каждую фичу**, перечисленной руками ([bulletproof-react](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)). FSD: изоляция срезов внутри слоя плюс формальный escape hatch `@x` — когда сущности действительно связаны (владение, вложенность), срез экспонирует отдельный cross-import public API (`entities/artist/model/artist.ts` импортирует из `entities/song/@x/artist`), что «makes the connection between the entities explicit and side-steps the slice isolation», **документируя** связность, требующую согласованного рефакторинга ([FSD Layers](https://feature-sliced.design/docs/reference/layers)). Формулировка спора: **Bulletproof устраняет связность инверсией, FSD сохраняет её как документацию.** Ни один из источников не разбирает подход другого. Стоимость каждой стороны задокументирована: у Bulletproof — ручная зона на фичу, которая не масштабируется без кодогенерации; у FSD — проблемы именования срезов и выбора между `lib` и `model`, потеря продуктивности на этапе обучения, более высокий порог входа (⚠️ это третьесторонние оценки уровня search-synthesis, не официальная FSD — [dev.to](https://dev.to/algoorgoal/feature-sliced-design-review-22k0); [codecentric](https://www.codecentric.de/en/knowledge-hub/blog/feature-sliced-design-and-good-frontend-architecture)).

### Спор 3. Bulletproof React против FSD: легальны ли категорийные имена папок

Bulletproof React **сохраняет** `utils`, `types`, `hooks`, `components` как общие верхнеуровневые папки и делает их безопасными, **принуждая направление** импортов линтером. FSD эти имена **запрещает** и делает безопасность за счёт **принуждения назначения**: «`components`, `hooks`, and `types` are bad segment names because they aren't that helpful when you're looking for code» ([FSD Slices and segments](https://feature-sliced.design/docs/reference/slices-segments)). Спор реален, но **не непримирим механически**: конфиг ESLint-зон ортогонален именованию сегментов, так что проект вправе взять именование FSD внутрь механизма принуждения Bulletproof React. Есть и частичное примирение по существу: `utils/format/date-time/` у Wieruch и «one area of focus, for example, dates, colors, text manipulation» у FSD описывают **одну и ту же** внутреннюю организацию — расходятся только в том, можно ли внешнюю папку звать `utils`. Единственное не-фольклорное различие между `lib` и `utils` тоже фиксируется здесь: у Bulletproof React `lib` — «Preconfigured reusable libraries», у FSD `shared/lib` — набор сфокусированных внутренних библиотек с README на каждую; в обоих случаях `lib` означает **сконфигурированную интеграцию или настоящую внутреннюю библиотеку**, а не мешок функций.

### Спор 4. Нужен ли фронтенду domain layer — «адвокатура написана лучше, отказ внедрён шире»

**За.** Alex Bespoyasov даёт наиболее полную трактовку: три слоя по близости к доменному знанию — Domain (сущности и чистые преобразования, «The domain is the core that distinguishes one application from another»), Application (use cases, оркестрирующие домен через **ports**), Adapters (конкретные интеграции), с правилом «**Only the outer layers can depend on the inner layers**» ([Bespoyasov, 2021-09-02](https://bespoyasov.me/blog/clean-architecture-on-frontend/)). Alex Kondov обосновывает слои темпом изменений, а не чистотой: «We add layers because different kinds of logic change at a different pace, and they shouldn't impact one another», и «The visualization code is our interface to the browser. When, how, and what data we need is part of our domain logic. They have no place being together» ([Kondov, 2024-02-09](https://alexkondov.com/full-stack-tao-clean-architecture-react/)). Показательно, что **оба** сами навешивают ограничители: Bespoyasov — «A full implementation will be an overkill that will increase the entry threshold for newcomers» и «If it's more pragmatic… to break a rule, I'll break it», с «минимально жизнеспособной» версией (выделить домен и соблюдать направление зависимостей); Kondov — «**Software Design Must be Pragmatic**», начни с черновика.

**Против.** Сильнейшее возражение по существу: Clean Architecture становится вредной, «when it treats React as an annoying detail to be hidden, since React isn't the domain but is a real part of the frontend model — rendering, interaction, cache coordination, forms, focus, and loading states all depend on the framework», плюс возражение по цене изменений — «adding a new field to a form shouldn't require updates to five different files and a schema migration» ([Medium-критика](https://medium.com/@mernstackdevbykevin/clean-architecture-for-frontend-sounds-smart-until-you-ship-62f9ccf54030)). ⚠️ Авторитет этого источника низкий: аргумент цитируемый, автор без статуса — в skill его надо атрибутировать как «распространённая критика», а не как позицию эксперта. Наиболее авторитетный голос, работающий на этой стороне, — Dan Abramov против абстракции-для-порядка в целом: «My code traded the ability to change requirements for reduced duplication, and it was not a good trade» ([Goodbye, Clean Code](https://overreacted.io/goodbye-clean-code/)) — но это не прямое опровержение Clean Architecture на фронтенде, и преувеличивать нельзя. А **контр-консенсус, который реально победил на практике**, состоит в том, что ни у Bulletproof React, ни у Wieruch — двух самых тиражируемых структурных референсов — **нет** папок `domain/`, `usecases/` или `ports/` вообще.

Собственная формулировка заметок — и лучшая честная сводка спора: **«advocacy is better written, rejection is better adopted»**. Исследователь прямо фиксирует, что **не нашёл** ни одной статьи высокого авторитета с центральной тезой «фронтенду не нужен domain layer»: оппозиция живёт в практике, а не в прозе. Два аргумента дополняют картину. Первый — обоюдоострый тест Фаулера: типичный фронтендовый «домен-слой» — это Zod-схемы плюс функции-мапперы, то есть ровно «little more than bags of getters and setters», а Anemic Domain Model «incur[s] all of the costs of a domain model, without yielding any of the benefits» ([Fowler, 2003-11-25](https://martinfowler.com/bliki/AnemicDomainModel.html)) — то есть канон паттернов, который заимствует адвокатура, режет **против** большинства её реализаций. Второй — настоящая разделительная линия не «слои: да/нет», а **где живут инварианты**: когда инварианты принадлежат серверу (обычный SPA/BFF-случай), моделировать на фронтенде нечего и домен-слой — церемония; когда клиент владеет реальными правилами (offline-first, редакторы, CAD/дизайн-инструменты, конфигураторы цен, локальная симуляция), позиция адвокатов существенно сильнее — и показательно, что документация TanStack независимо выделяет именно «design tools» как случай, всё ещё требующий существенного client-owned синхронного состояния ([TanStack Query docs](https://tanstack.com/query/latest/docs/framework/react/guides/does-this-replace-client-state)).

### Спор 5. Radix `asChild` против Base UI `render` — живое расхождение двух библиотек первого эшелона

Radix: «When `asChild` is set to `true`, Radix will not render a default DOM element, instead cloning the part's child and passing it the props and behavior required to make it functional», с обязательствами на стороне потребителя — разложить все props на нижележащий DOM-узел и пробросить ref, — и с переносом ответственности: «If you do decide to change the underlying element type, **it is your responsibility to ensure it remains accessible and functional**» ([Radix Composition](https://www.radix-ui.com/primitives/docs/guides/composition)). Base UI (команда MUI, v1.8.0) решает ту же задачу prop'ом `render`, принимающим элемент **или функцию**; контракт потребителя идентичен («The custom component must forward the `ref`, and spread all the received props on its underlying DOM node»), а функциональная форма «gives you complete control over spreading props and also allows you to render different content based on the component's state» ([Base UI Composition](https://base-ui.com/react/handbook/composition)). Ключевое наблюдение: **контракт на потребителя у обоих одинаковый**, значит спор про эргономику и вывод типов, а не про семантику. Заявленные причины выбора Base UI (лучший TS-inference, более явное слияние props, проще отладка) исходят из низкоавторитетного источника и **не** подтверждены первоисточником — сам `render` подтверждён, мотивировка нет ([Maryan Mats](https://maryanmats.com/blog/render-props-are-not-dead/)). Смежный спор того же семейства: patterns.dev утверждает, что «in a 2025 codebase, render props are no longer the default tool for sharing logic — custom hooks are» ([patterns.dev](https://www.patterns.dev/react/render-props-pattern/)), тогда как Base UI v1.x делает `render` **основным** API — и оба верны, потому что говорят о разных задачах: разделение логики против контроля над рендерингом, и хук «can give you state but cannot wrap your JSX in component boundaries».

Дополнительно стоит зафиксировать, что **сама граница дизайн-системы — это спектр степени инверсии контроля**, и четыре библиотеки дают четыре разных ответа на один и тот же `Button`: behavior-only с возможностью подмены корня (Radix), behavior-only с render-prop (Base UI), стилизованные компоненты с документированными escape hatch `xxxProps`/`xxxComponent`/`xxxRef` (MUI), и владение исходниками — «This is not a component library. It is how you build your component library» (shadcn/ui). Skill должен требовать от проекта **назвать**, какая из четырёх моделей у него, потому что от этого зависит props-API всех компонентов.

## Негативные результаты: чего в источниках нет, и это находка, а не пробел

Это раздел, ради которого skill не будет выдавать фольклор за факт. Каждый пункт — проверенное отсутствие.

**У react.dev вообще нет страницы про структуру проекта.** Единственное официальное высказывание React живёт на `legacy.reactjs.org`, и у него **нет** преемника на react.dev. Это настоящая дыра в первоисточниках, а не неудача поиска ([React legacy docs](https://legacy.reactjs.org/docs/faq-structure.html)).

**Ни один авторитетный источник не одобряет раскладку `utils` = generic / `helpers` = domain-specific.** Тиражируемая формулировка «A helper is something specific to a given project, while a utility is a generic function that accomplishes an abstract task» происходит из личного блога, который на момент исследования отдавал **HTTP 503**, так что даже её точная формулировка не проверена ([Stephen Charles Weiss](https://stephencharlesweiss.com/utils-vs-helpers/)); те же слова без ссылки на авторитет повторяются на dev.to, в GitHub-issue 2016 года и в постах 2024-го. При этом **противоположная** сторона укомплектована именами: Fowler — «Usually I treat the word 'helper' on a class as a red flag as it usually indicates a poorly thought out abstraction» ([Embedment Helper, 2007-03-26](https://martinfowler.com/bliki/EmbedmentHelper.html)); Cheney — разбор `utils`/`helpers`/`base`/`common` как проектного провала ([2019-01-08](https://dave.cheney.net/2019/01/08/avoid-package-names-like-base-util-or-common)); FSD — «lib folders should not be treated as helpers or utilities», с требованием одной области фокуса на библиотеку и README с описанием назначения ([FSD Layers](https://feature-sliced.design/docs/reference/layers)). Честный вывод для skill: **это командная конвенция, а не стандарт**, и если в кодовой базе есть обе папки, граница между ними не выживет контакта с новыми разработчиками.

**Нет ни одного авторитетного порога по количеству строк для дробления компонента.** Ни react.dev, ни MUI, ни Radix, ни Base UI, ни Next.js такого правила не содержат; «150/200/250 строк» встречаются только в низкоавторитетных блогах. То же касается **числа props**: авторитетного лимита «больше N props — дроби» нет. Нет и официального правила «один компонент на файл».

**Нет авторитетного «правила трёх» для продвижения компонента в shared.** Правило трёх — общая рефакторинговая максима, а не утверждение React-литературы о структуре: та говорит «второй потребитель» (Wieruch: «two or more features need it») или «used on multiple pages» (Profy.dev). Формулировка «rule of two», которая ходит по сообществу, получена **синтезом результатов поиска**, а не из одной проверенной первичной страницы. Отдельно: критерий «3+ мест» действительно встречается, но **в литературе про дизайн-системы**, у практиков вроде EightShapes и Salesforce UX, и это Medium-посты, а не версионированная документация. Существует и прямой **контр-норматив**: дублировать, пока переиспользование не доказано (собственный источник заметок — снова community synthesis, без атрибуции). Напряжение «продвигать на втором использовании» против «дублировать до доказательства» в литературе **не разрешено**, и это самое честное, что можно доложить: методологии расходятся в том, принимать ли решение человеком или отдать его тулингу.

**«God component», «fat component» и «god hook» — фольклорные термины без авторитетных определений.** Ближайшее к ним из уровня экспертов — у Kondov: «Pulling all the logic in a few components leads to bloat» и «If a part of the markup is complex, requires loops and conditionals — extract it» ([Tao of React](https://alexkondov.com/tao-of-react/)). В skill «god component» следует подавать как **композит из документированных запахов** (много несвязанных ответственностей против правила separation of concerns из Thinking in React, плюс взрыв флагов, плюс внутреннее ветвление), а не как термин искусства.

**react.dev явно ДОПУСКАЕТ prop drilling.** «It's not unusual to pass a dozen props down through a dozen components. It may feel like a slog, but it makes it very clear which components use which data!» ([Passing Data Deeply with Context](https://react.dev/learn/passing-data-deeply-with-context)). Любое правило skill, объявляющее drilling антипаттерном как таковой, противоречит официальной документации; антипаттерн — только **транзитный** prop через компоненты, которые его не используют.

Остальные подтверждённые отсутствия, короче: **нет** первоисточников от Vercel, Shopify, Airbnb или Spotify по таксономии React-папок — заявления о «одобрении бигтехом» любой методологии не подкреплены; **нет** ни одной официальной страницы Next.js, которая называла бы, оценивала или рекомендовала вариант «каждый `page.tsx` — `"use client"`» (документационная пустота, а не скрытая позиция); **нет** авторитетного источника, связывающего FSD или Bulletproof React с границами RSC/`"use client"` — все названные методологии по этому вопросу молчат, хотя именно он сильнее всего определяет размещение файлов в Next.js-приложениях; **нет** конференционного доклада или RFC про структуру проекта React (RFC-процесс React этой темы не касался); **нет** авторитетного React/TypeScript-источника о превращении helper-функций в методы доменной модели (классика — Fowler 2007 и Cheney 2019, то есть экстраполяция); **нет** официального заявления Zod о схемах как единственном источнике истины для типов — возможность вывода документирована, архитектурная рекомендация нет; **нет** авторитетного источника за или против сгенерированных API-клиентов (openapi-typescript, orval, tRPC) как архитектурного выбора; **нет** официального высказывания о колокации тестов, stories и фикстур внутри `app/` (правило колокации это подразумевает, но документация слова «tests» не произносит); **нет** официального указания, передавать ли доменный объект (`user`) или его поля как props; **нет** источника, измеряющего **архитектурную** цену отказа от barrel'ов (churn от глубоких путей при перемещении файлов — утверждение, а не измерение); и **HOC как рекомендованный паттерн отсутствует в текущей официальной документации вовсе** — само отсутствие и есть находка, а выжившие применения (`connect`, `withRouter`) вытеснены хуками для логики и `asChild`/`render` для подмены элемента.

## Применимость к `client/` в DevDigest: что исследование поддерживает, что лишь терпит, и одна конкретная ловушка

Измеренная форма проекта: Next.js 15.1 / React 19 / TanStack Query 5 / next-intl / Zod; App Router используется как **чисто клиентский роутер** — 65 из 105 `.tsx`-файлов несут `"use client"`, **каждый** `page.tsx` является client component и читает параметры маршрута через `useParams()`, а не через prop `params`; единственный server component — корневой `layout.tsx`, он же держит единственный экспорт metadata; файлов `error.tsx` / `loading.tsx` / `not-found.tsx` нет нигде; route handlers и server actions отсутствуют; все данные приходят из отдельного Fastify API на :3001 через хуки TanStack Query.

**Что исследование прямо поддерживает.** Во-первых, сама архитектура данных: «External HTTP APIs» — одна из **трёх** рекомендованных Next.js архитектур, и она названа подходящей именно тогда, когда «Separate backend teams use other languages or manage APIs independently», под моделью Zero Trust ([Data security](https://nextjs.org/docs/app/guides/data-security)). Во-вторых, следствие из правила «choose one data fetching approach and avoid mixing them»: раз выбран внешний API, **отсутствие** Next-side DAL, route handlers и server actions — это соблюдение правила, а не пробел; авторизация обязана жить в Fastify, и добавлять частичный DAL поверх было бы отступлением от документации. В-третьих, TanStack Query как клиентский кэш благословлена официально, с отдельной под-страницей руководства и таблицей паттернов, и её основание сформулировано документацией так: библиотека нужна, «when Client Components need a **shared browser cache**» ([Client-side data fetching](https://nextjs.org/docs/app/guides/client-side-data-fetching)). В-четвёртых, SPA на App Router — «**Next.js fully supports building Single-Page Applications (SPAs)**» ([SPA guide](https://nextjs.org/docs/app/guides/single-page-applications)). В-пятых, схемы Zod как общий контракт и `z.infer` вместо параллельного рукописного типа — это ровно та практика, которую отчёт называет прагматичной заменой домен-слоя.

**Что исследование лишь терпит.** Конкретный вариант «каждая страница — `"use client"`» **валиден, но не одобрен**: каждый ингредиент задокументирован по отдельности (`useParams` — санкционированный Client-хук; TanStack Query — первоклассная опция; внешний API — одна из трёх архитектур), но **ни одна официальная страница не называет, не оценивает и не рекомендует** эту комбинацию, а все пять документированных SPA-паттернов начинаются в Server Component — флагманский из них стартует запрос в `app/layout.tsx` без `await` и передаёт Promise в клиентский провайдер, чтобы «avoid client-side request waterfalls». `useParams()` против prop `params` — оба текущие, ни один не deprecated. Отсутствие `error.tsx`/`loading.tsx`/`not-found.tsx` документация не запрещает, но эти конвенции существуют ровно для того, чтобы роутер **устанавливал** за вас error boundary и Suspense boundary; без них все состояния ошибок и загрузки приходится держать внутри компонентов вручную. Два ограничения стоит знать даже без плана менять архитектуру: `"use client"` **не** отключает SSR — клиентские компоненты всё равно prerender'ятся при `next build`, так что страницы рендерятся дважды, если явно не отказаться через `next/dynamic` с `{ ssr: false }`; и содержимое, доступное только после выполнения JS, невидимо краулеру, который JS не исполняет — «SEO depends on whether the server render reaches the content» ([Server and Client Boundary](https://nextjs.org/docs/app/guides/server-and-client-boundary)). Приятный вывод: конфигурация «единственный server component — root layout» и есть **та самая форма**, которую предполагает флагманский официальный SPA-паттерн, то есть проект находится в одном шаге от документированной SPA-архитектуры, не отказываясь от клиентского слоя данных.

**Одна конкретная будущая ловушка, названная заметками.** Под `cacheComponents` `useParams` **приостанавливается и роняет сборку**: «Routes with dynamic params not covered by `generateStaticParams`: the param is not known until request time. **`useParams` suspends. Wrap the component (or a parent) in a `Suspense` boundary … otherwise, the build fails.**» ([useParams API reference](https://nextjs.org/docs/app/api-reference/functions/use-params)). Поскольку в проекте **каждая** страница читает параметры через `useParams()`, он привязан к тому, чтобы держать `cacheComponents` выключенным, либо к оборачиванию каждой такой страницы в `<Suspense>`. Чтение параметров через prop `params` этой оговорки не несёт.

## Заключение

Главное, что меняет понимание: **отсутствие официального канона — не лакуна, которую skill должен заполнить уверенным тоном, а сама структура проблемы.** У React нет страницы про структуру проекта; Next.js отказывается быть opinionated; ни одна из названных методологий — FSD, Bulletproof React, Atomic Design, Screaming Architecture — не проектировалась под ограничение, которое сегодня сильнее всего определяет размещение файлов в Next.js-приложении, то есть под транзитивную границу `"use client"`. Это значит, что самая ценная часть skill — не список папок, а **два механизма и один тест**: граница как ошибка компиляции (`server-only`, lint-зоны, публичный API среза) вместо границы как договорённости; именование по назначению вместо именования по категории; и проверка «предсказывает ли имя модуля его содержимое». Всё остальное — выбор степени церемонии, и он должен зависеть от размера команды и продолжительности жизни кода, а не от того, чья статья убедительнее написана.

Второе следствие, менее очевидное: **дедупликация запросов развернула архитектурное давление вниз, и это обесценило целый пласт правил 2015–2019 годов**. Container/presentational отозван автором; «только контейнеры загружают данные» устарело и для RSC, и для клиента с кэшем; HOC исчезли из официальной документации, не будучи формально осуждёнными; авторизация в middleware из паттерна превратилась в уязвимость с CVSS 9.1. Skill, который просто соберёт «лучшие практики React», с большой вероятностью соберёт этот отменённый пласт, потому что его больше всего в интернете. Отсюда практический вывод для следующего шага: список запретов из раздела «не повторять» и список подтверждённых отсутствий должны попасть в skill **раньше** любых рекомендаций — потому что задача скилла на 2026 год не столько подсказать, что делать, сколько не дать модели уверенно повторить фольклор. Что касается `client/` в DevDigest, картина непротиворечива: выбранная архитектура данных (внешний Fastify API, авторизация на бэкенде, TanStack Query на клиенте) прямо санкционирована документацией, а всё, что можно улучшить, — это не редизайн, а две локальные вещи: границы, которые роутер готов установить бесплатно (`error.tsx`, `loading.tsx`, `not-found.tsx`), и осознанное отношение к связке `useParams()` + `cacheComponents`, которая когда-нибудь уронит сборку.
